## 一、§7 自定义真实场景生成 (P3-b / P3-c)

### 1.1 核心架构决策: 场景分表 + 领域视图

§7.5 原文「**不落 `practice_scenarios` 主表** (那是公共 seed 库)」. 这条边界由**物理分表**保证,
而不是靠 "在主表里用 `user_id` 区分" 的约定 —— 因为主表的 `enabled` 列承担着**审核闸门**语义
(共享库里每一条都过审), 一旦把未审核的 LLM 现场产出混进去, 这条不变式立刻失效.

代价是「一个可练习的场景」有了**两个物理来源**, 于是引入 `PracticeScenarioView` 作为唯一领域抽象:

```
practice_scenarios (共享库)         practice_custom_scenarios (私有库)
        │                                      │
        └──────────► domain/practice/practice-scenario-view.ts ◄──────┘
                          │  toScenarioView() / toCustomScenarioView()
                          ▼
        scenario service / evaluator / attempt service  (上层零分支)
```

新增第三种场景来源时只需再写一个投影函数, 上层零改动.

### 1.2 数据层

| 项 | 内容 |
|---|---|
| 新表 | `practice_custom_scenarios` (14 列 + 3 索引) |
| 新列 | `practice_attempts.scenario_source` (varchar 20, 默认 `seed`) |
| 新列 | `practice_attempts.attempt_ordinal` (int) —— §8.5 E1 取号原子化 |
| 新列 | `practice_attempts.ability_dimension_code` / `ability_signal` —— §7.6 P3-c 画像回写 |
| 新索引 | `uniq_pa_user_scenario_ordinal` (user_id, scenario_id, attempt_ordinal) UNIQUE |
| 新索引 | `idx_pa_user_ability` (user_id, ability_dimension_code) |
| 列放宽 | `quota_usage.period` VARCHAR(7) → VARCHAR(10) (容纳日粒度 `YYYY-MM-DD`) |
| migration | `1714900000016-AddPracticeCustomScenarios.ts` (幂等: 列/索引均先查后改) |

私有表的关键列: `exercise_mode` (路由主键) + `exercise_id` (§7.2 的 `exerciseId`) + `source_payload`
(用户三问原文, **原样保留不脱敏**) + `generated_scenario` (LLM 输出) + `generation_mode`
(`llm` / `template`, 用来事后查"模型退化比例").

### 1.3 两个端点 (§7.2)

```
POST /counselor/practice/scenarios:generate   → GeneratedCustomPracticeScenarioDto
GET  /counselor/practice/scenarios/mine       → CustomPracticeScenarioListDto
```

- 路由冒号用转义写法 `scenarios\\:generate`: Express 5 的 path-to-regexp v8 会把裸 `:generate`
  当成**路由参数名**, 转义后才是真正的字面量冒号 (params 为空).
- 响应体同时给 `id` 与 `scenarioId` (同值): spec §7.2 的示例叫 `id`, §3.2/§3.5 叫 `scenarioId`,
  两个都给, 免得客户端两边猜.

### 1.4 §7.3 LLM 生成约束 (写进 system prompt)

1. **脱敏** —— 人名/地名/单位名一律不出现; `personaName` 用代称 (他/她/TA); `personaNote` 只留
   年龄/性别/议题
2. **零压** —— `commonErrors` 只描述技术动作, 绝不评价用户当时的回应
3. **贴近真实** —— `openingLine` 忠实于原话原意, 禁止教科书化
4. **stuckPoint 对齐 rubric** —— 用户说"冷场"必须出一条"是否给出继续展开的邀请";
   说"说教"必须出一条"是否在给建议"
5. **可练习性** —— 维度 3-5 条, 每条都能被措辞判定

### 1.5 §7.4 配额与降级 (零压红线在可用性维度上的同一条原则)

| 触发条件 | 降级产物 | `degradedReason` |
|---|---|---|
| 今日生成次数用完 | 标准题库里的一个场景 | `quota_exceeded` |
| 私有场景条数达上限 | 标准题库里的一个场景 | `storage_limit_reached` |
| LLM 失败 / 超时 / 开关关 | 确定性模板场景 (用用户原话) | `generation_unavailable` |

**三条降级路径全部返回 200 + 一条可练的场景**, 不抛异常. §7.4 原文「超额时前端不弹『今日已用完』
红条, 而是软降级回标准题库」.

配额口径: 复用 `quota_usage` 表 (spec §7.4 原文), 但**不复用** `BillingService.consumeQuota`:
后者是会员档位的**月度**配额、limit=0 时直接 throw (硬拒绝), 与本需求的**日粒度 + 软降级**语义冲突.
故练习域自建 `PracticeQuotaService`, 配额类型走独立的 `PracticeQuotaType` (不污染跟客户端 1:1 wire
的 `QuotaType`, 也不让会员状态接口多吐一行"余额 0"权益).

扣减用**单条条件 UPDATE** (`SET used = used + 1 WHERE used + 1 <= \`limit\``): 读改写写法在并发下会
少扣或超扣.

### 1.6 §7.6 P3-c attempt 回写五维画像

10 档基本功 → `ability_dimensions.sub_indicator_code` 的**显式映射表**
(`config/practice-ability-mapping.ts`), 不做运行时模糊匹配.

单次信号: ✅ 计 +1, ⚠️ 计 -1, ℹ️ **不计入** (技术提示是概念提醒, 不是"做到没做到"的判定);
跨次**取均值**而非最近一次 (一次手生不该让雷达崩掉). 回写失败**不影响练习主链路**.

零压边界: 信号只进 `ability_scores`, **不出现在任何 practice 出参 DTO** —— §6.2 在出参层仍是结构性保证.

### 1.7 §3.5 旧入口并轨

§3.5 (`POST /custom-scenarios`, mode + situation) 与 §7.2 (`POST /scenarios:generate`, 三问) 现在
**共用同一张表 + 同一条落库链路 + 同一套降级策略**, 由 `PracticeCustomScenarioService` 收敛.
否则用户会发现"从两个入口生成的场景, 只在一个列表里能看到".

## 二、§8 审计清单修复

### 2.1 §8.4 MCQ 备考频道

| # | 项 | 处理 |
|---|---|---|
| 1 | 未知 id 返回 404 | 原本已正确 (`findOneExercise` → NotFound), 未改 |
| 2 | 列表响应形态 | 原本已稳定为 `{ items, total }`, 未改 |
| 3 | **difficulty 字面量** | **已修**: query 兼容大小写 (`@Transform` 转大写后校验), 响应体固定大写 `L1/L2/L3` |
| 4 | type/mode 枚举一致 | 原本已与 §3.1 同源, 未改 |
| 5 | 答案字段隔离 | 原本已不下发 `correctOptionIndex`, 未改 |
| 6 | 分数口径隔离 | 原本已隔离 (MCQ 有分 / 自由练习无分), 未改 |

第 3 项的取值依据 (前端真实解析代码 `training_exercise_repository_impl.dart:485-487`):

```dart
final difficulty = TrainingDifficulty.values.firstWhere(
  (d) => d.name.toUpperCase() == difficultyValue,   // 客户端自己转大写再比
```

即**只有大写响应能被解析命中**; 而客户端**发出去的** filter 是 `difficulty.name` (小写 `l1`).
所以正确方向是: **query 放宽 (兼容大小写), 响应收紧 (固定大写)**.

### 2.2 §8.5 跨频道边界与缺陷

| # | 项 | 处理 |
|---|---|---|

| A2-A5 | 进度端点 / attempt 表 / 无分 / 枚举复用 / 引擎归属 | 结构性保证已在, 本轮未新增违规路径; 私有场景的 `source` 字段只出现在 practice 频道 |
| B1 | turn ≤ expectedTurns | **已修**: service 层比对, 越界抛 `BizCode.PracticeTurnOutOfRange` (400) |
| B2 | situation trim + 私有场景条数上限 | **已修**: 入参先 `@Transform` trim 再校验; 新增 `PRACTICE_CUSTOM_SCENARIO_MAX_COUNT` (默认 50) |
| B3 | duration/record 0 的语义 | **已修**: 明确 0 合法 —— `durationSeconds=0` = 秒答秒交; `recordSeconds=0` = 没录到有效音频 (不折算语速). 负数仍由 `@Min(0)` 拦掉 |

| E1 | attemptOrdinal 并发 | **已修**: 取号 + 落库进**同一短事务**, 事务内悲观写锁锁住 `(user_id, scenario_id)` 行区间 (间隙锁让并发插入串行化); 序号按 `MAX(attempt_ordinal)+1` 取 (**不按 COUNT** —— COUNT 漏软删行会撞唯一键); DB 侧另有 UNIQUE 约束兜底. LLM 评判在事务外, 锁只持有毫秒级 |
| E2 | 空库 vs 无权访问 | **已修**: 拆成 `BizCode.PracticeScenarioPoolEmpty` 与 `BizCode.PracticeScenarioNotFound`, 前端可分别显示"题库正在补充中"与"场景不存在" |
