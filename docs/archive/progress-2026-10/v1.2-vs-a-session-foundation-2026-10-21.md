## 2. 3 个从 MiniMax 官方文档读出来的、改变了实现方案的事实

| # | 文档事实 | 对实现的改写 |
|---|---------|-------------|
| 1 | **M3.1-Flash 忽略 `temperature` / `top_p`**（固定 1 / 0.95） | 排期里原写的「督导 temperature=0.3」「轻提示 temperature=0」**作废**。改为：确定性靠 prompt 约束，思考量靠 `reasoning_effort` 分档（`supervision` 用 `high`） |
| 2 | **thinking token 计入生成长度上限**，设小则 `finish_reason=length` 且 `content` 为空 | 结构化 JSON 改用 `max_completion_tokens`（新字段），`supervision` 给到 8192，给 thinking 留足余量；不再用会截断的 `max_tokens` |
| 3 | **M3.1-Flash thinking 走独立 `reasoning_content` 字段**（`content` 干净），但 **M3 系列的 `<think>` 内联在 `content` 里** | 现有 SSE 解析只取 `delta.content` → M3.1-Flash 天然干净；为防模型配置回退到 M3，`extractJsonPayload` 防御式剥 `<think>` 块 |

另：官方文档确认 `reasoning_effort` **仅 M3.1-Flash 生效** → `supportsReasoningEffort(model)` 按模型名判断，只在支持时才下发该字段，避免上游 400。

## 4. 第 1 轮 build 修复 (2026-10-21 14:40, 大炮手动跑 `npm run build` 反馈)

大炮跑 `npm run build` → **12 错, 全在 1 个文件** `src/counselor/providers/supervision.service.ts`
（其余 13 个改动文件全部编译通过）。按仓库「迭代式 5 段治本」惯例，本轮修复**另起一段注释**，不改写上一轮。

| 错误 | 数量 | 根因 | 修法 |
|------|------|------|------|
| TS4111 `Property 'x' comes from an index signature, so it must be accessed with ['x']` | 11 | 项目 `tsconfig.json` 开了 `noPropertyAccessFromIndexSignature: true` → 对 `Record<string, unknown>` 做**点访问**会报错。我写 `validateSupervisionPayload` 时用点号取 7 个字段，漏判这个编译开关 | 全部改方括号：`obj['overallScore']` / `turn['sentence']` / `turn['score']` …；**运行时行为完全不变**（JS 里 `obj.x` ≡ `obj['x']`） |
| TS2345 `Argument of type 'string \| null' is not assignable to parameter of type 'string'` | 1 | `SupervisionSchool.promptTemplate` 实体声明是 `string \| null`（DB 列可空，运营还没填模板的流派就是 null），我给 `buildSchoolSystemPrompt` 的入参写了 `string` | 入参改 `string \| null`，内部 `template && template.trim().length > 0` 判空，null / 空串 / 纯空白统一走内置通用督导 prompt 兼底 |

**踩坑教训（已进本轮 5 段治本注释）**：写 TS 前必须先看 `tsconfig.json` 的严格开关清单。本项目除 `strict` 外还开了 `noPropertyAccessFromIndexSignature` / `noUnusedLocals` / `noUnusedParameters` / `noPropertyAccessFromIndexSignature` / `noImplicitReturns` —— 其中 `noUnusedLocals: true` 意味着**未使用的 import 是 tsc 错误不是警告**（这也是我写只读静态检查脚本的原因）。写完后全仓扫 `as Record<string, unknown>`：其余 9 处既有代码（`agent/supervisor/supervisor.service.ts` / `common/security/*.interceptor.ts` / `counselor/seeds/training-exercises.seed.ts`）**本来就是方括号写法**，只有我新写的这 1 处踩了坑。

**未用压错手段**：不写 `@ts-expect-error` / `@ts-ignore`（那是把编译期约束藏起来，下一个人复制这段代码会再踩）；不把 `Record<string, unknown>` 改成 `any`（会连带关掉后续所有类型检查）。

## 6. 关键设计决策（供 review）

| # | 决策 | 理由 |
|---|------|------|
| D1 | 督导 **不保留 mock 兜底**，LLM 失败抛 503 且**不落库** | 假分数会被学员当成真实督导结论去改技术动作，比报错更糟 |
| D2 | 重复生成改 **upsert**（原代码每次 insert） | `supervision_feedback` 有 `UNIQUE(session_id, session_type, school_id)`，旧代码第二次生成必撞唯一索引；顺带解决 client 重试 / BullMQ 重试 |
| D3 | `finish` **不**同步生成督导，改 BullMQ 异步 | 真接 LLM 单次 30-120s，同步会拖死 HTTP 连接；client 轮询既有 `GET /counselor/supervision/feedback/:sessionId/:sessionType` 取结果 |
| D4 | 新队列 `counselor-supervision`，**不复用** agent 的 `supervisor` | agent 队列的 payload 是 `RunReportInput` 且落 agent 自己的表，同名会让 job 被错消费 |
| D5 | 状态机守卫放 **domain 纯函数**，不在 service 的 if 里 | v1.2 §10.1 初访分流 / §11.3 暂停休息 / BullMQ 收尾是 3 个消费方，必须单一真值源 |
| D6 | 会话上下文**统一成 `SessionContextTurn` 3 字段** | 单次训练（5 字段）与长程卷宗（3 字段）两种 transcript 形状不同，entity 不能改，在上下文层收敛 |
| D7 | controller 的 DTO **值导入**（不用 `import { type X }`） | 全局 ValidationPipe 开了 `transform + whitelist`，靠 `design:paramtypes` 元数据拿 DTO 类；type-only 导入会让元数据退化成 `Object` → **校验静默失效**。仓库既有 `supervision.controller.ts` 就有这个坑（本轮未改，属独立修复范围） |
| D8 | prompt 占位符替换用**函数形式** `replace(/x/g, () => str)` | 渲染块内容可能含 `$&` / `$1` 等特殊替换模式，字符串形式会被吃掉导致画像/逐字稿被篡改 |
