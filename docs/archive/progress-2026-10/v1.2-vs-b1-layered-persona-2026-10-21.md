## 3b. 第 1 轮 build 修复 (2026-10-21 15:26, 大炮手动跑 `npm run build` 反馈)

大炮跑 `npm run build` → **31 错, 3 个文件**。实际只有 **3 个根因**, 其中 1 个级联出 27 个错。

### 根因 1 (27 错, 级联): `VisitorFullPersona` 同名冲突

- **现象**: TS2300 ×2 + TS2693 + TS2769 + TS2345 + TS2339 ×19 + TS2353 ×3
- **根因**: `visitor-persona.service.ts` 同时导入了两个 `VisitorFullPersona`:
  domain 侧的 **interface** (7 大块聚合) + entity 侧的 **class** (表行)。
  type-only 导入赢了类型位 → `@InjectRepository(VisitorFullPersona)` 拿不到值 (TS2693),
  entity 的 `id/caseId/displayName/trustLevel/createdAt` 全报不存在 (TS2339),
  `DeepPartial<VisitorFullPersona>` 认不出 `tenantId` (TS2769) —— 一个类型位错位炸出 27 个错.
- **修法**: domain 那个 interface **改名 `VisitorFullPersonaScript`** (剧本 = 内容);
  entity 类保持 `VisitorFullPersona` (表行是主公民, 跟仓库 11 个 entity 不带 `Entity` 后缀的风格一致).
- **反双胞胎**:
  - 不把 entity 改名成 `VisitorFullPersonaEntity` —— 破例会让新人以为有两种命名体系
  - 不靠 import 别名 (`as VisitorFullPersonaRow`) 糊过去 —— 能编译, 但两个概念在代码里仍同名,
    下一个人复制粘贴必再踩一次; 改名是治本

### 根因 2 (3 错): 模板字符串里的裸反引号

- **现象**: TS1005 ×2 + TS7005 (`'待补充' implicitly has an 'any' type`)
- **根因**: `visitor-persona-prompts.ts` 的 schema 说明是**模板字符串**, 我在提示词正文里写了
  `` `待补充` `` —— 反引号直接**终止了模板字符串**, 后面的中文变成裸代码.
- **修法**: 改成普通引号 `"待补充"`.
- **反双胞胎**: 不把整个 schema 说明从模板字符串改成普通引号拼接 —— 里面要插 `{}` 之类的说明,
  模板字符串是正确载体; 错的只是**内容里不该出现裸反引号**.

### 根因 3 (1 错): TS6133 未使用参数

- **现象**: `case-profile-entry.controller.ts:73` — `'caseId' is declared but its value is never read`
- **根因**: DELETE endpoint 的 `@Param('caseId')` 传进来没被用.
- **修法**: 拿它做**归属校验** (`entry.caseId === caseId` 才允许删), 而不是删参数.
- **反双胞胎**: 不删 `caseId` 参数 —— URL 里带着个案 id 却不校验归属, 等于能用 A 个案的 URL
  删掉 B 个案的条目 (只靠 userId 拦, 同一用户的多个案就穿透了); 也不靠 `_caseId` 改名压制 TS6133.

### 修复后回归核对

- 旧名残留: 所有 `VisitorFullPersona` 引用现在**全部指向 entity 类** (值引用正确)
- 改名落点: domain types 1 处 export + service 3 处引用, 一致
- 全仓同名符号扫描: `VisitorFullPersona` / `CaseProfileEntry` / `CaseProfileEntryLayer` /
  `SessionContextEntry` 各自**只有 1 个文件导出** → 无冲突
- 静态自审 (导入/导出/未使用/乱码/max-len 140): **0 问题**

## 3c. 第 2 轮 build 修复 (2026-10-21 15:30, 大炮手动跑 `npm run build` 反馈)

大炮跑 `npm run build` → **24 错, 2 文件**。根因仍是**同一个文件**的模板字符串。

### 根因: schema 说明的模板字符串**从来没闭合过** (22 错)

- **现象**: TS2362 / TS2304 / TS1005 / TS7005 / TS7031 / TS1434 / TS1160 (Unterminated template literal) —— 全部指向
  `visitor-persona-prompts.ts:50` 起的那个 schema 模板
- **真因链**（两轮叠加）:
  1. 第 1 轮: schema 块最后一行原文是 `` (如 "示例"、"xxx"、`待补充`)`; `` ——
     其中第 3 个反引号被当成了**模板闭合符**, 于是模板在那一行就"结束"了,
     块尾的 `;` 落在字符串外 → TS1005 + TS7005
  2. 第 1 轮我的修法: 把 `` `待补充` `` 换成 `"待补充"` —— **但同时把那个充当闭合符的反引号也删了**
     → 模板从第 50 行一路吞到第 125 行的 `` `- 来访者代号: ${...}` ``,
     解析器把 `${opts.displayName}` 当成插值、把 `来访者代号: ` 当成代码 → 22 个语法错
  3. 连带: `buildPersonaGenerationUserPrompt` 不再是合法导出 (TS2305),
     `VISITOR_PERSONA_SCHEMA_DESCRIPTION` 被解析成数值表达式 → TS2322
- **修法**: 在 schema 块**内容行之后**单独补一行 `` `; `` 作为模板闭合符 (第 107 行后).
  提示词正文里**不再出现任何反引号** (占位符示例改用普通引号).
- **反双胞胎**:
  - 不把整个 schema 说明从模板字符串改成普通引号拼接 —— 里面要插 `{}` 之类的结构说明,
    模板字符串是正确载体; 错的只是**内容里不该出现裸反引号** + **闭合符缺失**
  - 不用 `String.raw` 或转义 `\`` 糊 —— 那是在一个本不该有反引号的提示词正文里继续加复杂度

### 回归核对

- 反引号总数 **12 (偶数)** ✓; 两处多行模板闭合点核对: 31↔43 (system prompt) / 50↔107 (schema) ✓
- **新增语法级静态检查**（比前两轮的脚本硬一档）:
  用 node_modules 里已有的 `typescript` 做 `ts.createSourceFile()` **纯语法解析**（不类型检查、不 emit、不 build）,
  外加反引号奇偶校验 → 全部 18 个改动文件 **0 问题**.
  这一项能一次性拦住 TS1005 / TS1160 这类**语法事故**（前两轮共 28 个错全是这类），
  之前只查导入/导出/未使用的脚本查不出来.

## 5. 关键设计约束（防"看起来能跑、实际破防"）

| 约束 | 实现方式 |
|------|---------|
| 表层 PATCH **改不到深层字段** | 深层字段**连 DTO 都不存在** → `whitelist:true` 会剥掉，前端就算传了也进不来。这是 spec §4.2「不改未暴露字段」的**强保证**（不是靠 service 里 if 拦） |
| 用户**伪造不了**「来访者说过的话」 | `layer` 由**调用入口**决定：`create()` = 手写（`therapist_note`）、`appendDisclosed()` = AI 抽取（`self_disclosed`）。前端只能写手写层 |
| 上帝视角**默认关闭** | enum `GOD_VIEW_ENABLED` 默认 `false`；`getFull` 未开启直接 403，附带"先去偏好里开"的提示 |
| 未提及的信息**不占位** | 档案表「存在即已解锁」，没有行 = 空白（spec §4.2）；渲染块在无条目时返回空串 |
| 结构化输出**只有一条链** | 复用 VS-A 的 `CounselorLlmJsonClient`（收流 → 剥 think → 剥围栏 → parse → 业务校验 → 错误当数据不 throw） |
| 人设生成**失败不落脏数据** | 校验严格（7 大块任一结构不符即整份判非法），失败抛 503 且不写库 —— 半套人设会让 AI 依据不存在的事实做反应 |
| `trust_level` 存**长程级**不存长程历史 | 信任度随关系累积上升 → 存当前值，每场会谈结束回写；历史轨迹由 `case_profile_entries.sessionId` 承载，不另建时间序列表 |

## 6. VS-B2 需要一次架构拍板（★ 本片未做）

**问题**：v1.2 §4.3 要求「长程：注入 VisitorFullPersona 全量 + 当前信任度 + 已解锁 CaseProfileEntry 列表」到 **AI 来访者的 prompt**。

**代码现状（2026-10-21 核查）**：
- AI 来访者在 `src/agent/visitor/`，persona 来自 `src/agent/persona/` 的 `Persona` 实体 + **内存** Repository（`PersonaRepositoryMemory`），只认 `complaint/personality/background` 3 字段；
- counselor 端与 agent/voice 链路 **0 交集**（`grep -rn "voice\|agent" src/counselor/` 只命中注释）；
- visitor prompt 渲染点是 `visitor.prompts.ts` 的 `renderSystemPrompt(persona, memory)`，由 `VoiceService.startSession` → `VisitorService.openSession` 触发（WS `/voice/training/<sid>?token=...&personaId=...`）。

**3 个方案**：

| 方案 | 做法 | 代价 / 风险 |
|------|------|------------|
| **A. agent 侧直连 counselor 数据** | `VisitorService` 直接查 `visitor_full_personas` | ❌ 破坏单向依赖（`voice.module.ts` 明写"不在 VoiceModule 里 import 业务模块"）；agent 的 persona 是内存实现，跨存储后要重做 |
| **B. 依赖倒置 + provider token**（推荐） | agent/visitor 只提供"外部上下文插槽"（`renderSystemPrompt` 加 `extraContextBlock` 参数）+ 一个 `VISITOR_CONTEXT_PROVIDER` token；counselor 侧注册实现，**agent/voice 不 import counselor** | 沿用仓库既有 `PERSONA_REPOSITORY` token 先例；需新增 1 个 token 文件 + 1 个 provider 实现 + visitor 侧 1 处参数透传 |
| **C. counselor 自建长程来访者链路** | counselor 自己渲染 visitor prompt + 直连 LlmService | ❌ 会和 `agent/visitor` 形成**两套 visitor prompt**（重复代码 + 行为漂移）；且语音链路（ASR/TTS）在 voice 模块，会拉出第三套 |

**建议 B**。但有一个前置问题需要大炮拍板：**长程会话的 AI 来访者，现在走的是哪条链？**
目前 `training_sessions` / `long_term_cases` 与 WS `/voice/training` 之间**没有绑定关系** —— 前端是走 voice 链路（`sessionId` 直接用 counselor 的 session id），还是 counselor 自带对话链路（目前没有）？这决定 VS-B2 是「给 voice 链路加上下文注入」还是「counselor 自建链路再拉平」。
