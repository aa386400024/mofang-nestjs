## 2. 实现决策（spec ↔ 代码差异，8 条）

| # | spec 原文 | 落地做法 | 原因 |
|---|-----------|---------|------|
| **D9** | §6.4「AI 自动标记（来访侧）：后端在 transcript turn 上打 tag」 | **采集时机**绑在轻提示档位上：`light` 时逐轮采集（与提示**同一次** LLM 调用，零额外成本）；`off` 时**不采集** | `off` 的语义是"完全无提示"（§6.1）。若 `off` 仍逐轮跑 LLM 只为存标记，等于用户关了提示还在烧钱；且标记的**事后**价值由 VS-E 的督导 LLM 调用顺带产出（那次调用本来就要跑） |
| **D10** | §6.1「前端通过 SSE / WebSocket 拉取」 | **选 SSE**（`@Sse`），不选 WebSocket | ① 轻提示是单向推送，SSE 正是该语义 ② 复用 REST 鉴权（Bearer header），不必再写一遍 WS 握手鉴权 ③ 前端已有现成解析范式（`xin_su_app` `ai_engine/data/llm/llm_client.dart` 用 `http.Request` + `text/event-stream` 手动解析）→ 0 新依赖 ④ 走 WS 要么塞进 voice WS（voice → counselor 反向依赖，违反 `voice.module.ts` 既有原则），要么新开网关 + 前端再连第 2 条连接 |
| **D11** | §6.1 轻提示（classifier）+ §6.4 移情标记（打 tag）是两段需求 | **合并成 1 次 LLM 调用**，一次输出 `hint` + `mark` 两段 | ① 两者读的是同一段对话、发生在同一时刻 ② 每轮都跑，成本线性累加 ③ 更重要：两次独立判定可能自相矛盾（同一条回复，判提示说"没接住情绪"、判标记说"来访很平静"） |
| **D12** | §6.1 两档开关（用户可控） | 落既有 `counselor_ui_preferences`，`prefs` 值类型**放宽为 `boolean \| string`** + 加**值白名单** | 档位是字符串（`'light' \| 'off'`），与已有布尔偏好共存于同一 JSON 列。键白名单只能拦"未知键"，拦不住"已知键 + 非法值"（`{liveSupervisionHintTier:'garbage'}`）→ 必须加值白名单。放宽**不需要 migration**（列本身是 JSON） |
| **D13** | §6.1 / §6.2 / §6.4 三张表的 entity 草图（均无 tenant_id / user_id / deleted_at） | 3 张表**补齐** `tenant_id` + `user_id` + `deleted_at` | 跟 counselor 既有 12 个 entity 同一模板。多租户库里少一列租户字段 = 潜在越权口子（哪次查询忘了校验会话归属就跨用户泄露）。不接受"现在用不上"当省列的理由 |
| **D14** | §6.1 硬约束 4「同一类提示 5 分钟内不重复推送」 | 防抖 key = **(sessionId + category)**，查 **DB** 不查内存 | 不同类别的提示互不干扰（连续封闭式提问 + 自伤线索, 两类都要出）。查 DB 是因为多实例下内存态会失效，而 hint 表本来就存了 |
| **D15** | §6.3「督导 LLM 在生成 supervision_feedback 时, 额外输出一个 techStats JSON（复用同一次 LLM 调用, 不额外花钱），写在 long_term_case_sessions.supervisionFeedback 或 training_sessions 的新字段上」 | techStats 落 **session 表的 `tech_stats` 列**（不塞 `supervision_feedback.feedback` json）；**techStats 畸形不阻断督导反馈**（降级为 null，报告照常出） | 塞进 feedback json 会污染 4 字段的 1:1 wire（前端 DTO 读不到但数据在，以后排查踩坑），spec 本身也写的是"新字段"。主产物（督导反馈）不该被副产物（统计）拖垮 |
| **D16** | §5.4「`informed_consent_transcript` 存 4 要素覆盖明细」 | 判定结果**补齐缺失要素**（模型漏判 → 补 `covered=false`），不写半份 | 前端按数组长度算"已讲 N/4"，漏一个元素计数就错位；且"模型没提到某要素"在业务上就等于"没讲全" |

## 3. 关键设计约束（防"看起来能跑、实际破防"）

| 约束 | 实现方式 |
|------|---------|
| 轻提示**只给方向**（禁替代话术） | prompt 硬约束 + 校验层长度上限 500 + 类别枚举白名单 |
| 提示**默认关闭** | `liveSupervisionHintTier` 默认 `off`；`off` 时 worker 直接跳过，**不调 LLM** |
| 提示**不打断对话** | SSE 推送到侧边浮窗 slot，不弹窗（UI 侧由前端 shell 的 `overlay` 承担） |
| 同类提示 5 分钟不重复 | `(sessionId + category)` 防抖，查 DB |
| 用户**伪造不了** AI 判定 | `direction`（移情标记）/`layer`（档案条目）由**调用入口**决定，DTO 里根本没有该字段 |
| 知情同意结果**不污染**产品合规记录 | 写 `training_sessions` 新列，**不碰** `user_consents`（spec §5.3 正交） |
| 4 字段督导反馈契约 **0 破坏** | `supervision_feedback.feedback` 仍是 4 字段；techStats 走独立列 |
| 分析失败**不阻断**会话 | 写逐字稿成功即算业务完成；分析失败只记日志，不影响请求返回 |

## 4. 数据流（一次「来访者那一轮」）

```
客户端 PATCH /counselor/training-sessions/:id/transcript
   └─ 落 transcript (VS-A 已有)
   └─ 若新写入的是**来访者**那一轮 → 入队 BullMQ (jobId: ta-{sessionId}-{turnIndex})
        └─ worker: 读档位 (执行时读, 非入队时读)
             ├─ off → 跳过, 不调 LLM
             └─ light → 读最新 transcript → 取「来访这一轮 + 之前最后一句咨询师 + 最近 4 轮」
                  └─ 1 次 LLM (low 档) → { hint, mark }
                       ├─ hint → 防抖判定 → live_supervision_hints → SSE 推 → 前端侧边浮窗
                       └─ mark → transference_resistance_marks → SSE 推 → 前端标记时间线
```

| 前端 slot | 本片对应 |

| `topBarTrailing` / `sessionBadgeText` | 长程卷宗入口 /「第 N 次会谈」→ **VS-D** 范围 |

（`http.Request` + `Accept: text/event-stream` + `http.StreamedResponse` 手动解析 `data:` / `event:` 行）。
**不需要新依赖**（`http` 已在 pubspec，`web_socket_channel` 本片用不上）。

**知情同意环节**在长程/短程会话页的接入时机 → 前端侧决定（建议：进入初访前的前置步骤）。
