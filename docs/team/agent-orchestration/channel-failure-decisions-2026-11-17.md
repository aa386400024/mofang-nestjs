## 3. IM-023：通道失败的权威终态出口

**裁定：通道失败回滚 `ready`，不判任务 `failed`。**

| 维度         | 规定                                                                                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 权威出口     | `ready`（+`heldForHuman=true`，`releaseReason` 记录失败面）；`failed` 只给**不可恢复类别**（`fail-terminal`）                                                                                          |
| 判据         | 通道故障属**下游/工具平面**，任务业务结论未被否决；把投递失败判成任务 `failed` 会把通道噪声写进验收统计与返修计数                                                                                      |
| 与 §7 的关系 | 框架 §7「终态不重启」约束的是**任务终态**（`completed`/`failed`/`rejected`/`canceled`）。通道失败从未进入任务终态，故不受该条约束；一旦判 `failed`，就必须接受「终态不复活」，这正是本裁定要避免的浪费 |
| 例外         | 交付内容本身被证明不成立（不是送达问题）时，走 `fail-terminal`，并附不可恢复 `cause`                                                                                                                   |

实现对应：`scheduler.mjs#releaseFailedDeliveries` 的 `human-escalate` / 其余分支回滚 `ready`，仅 `fail-terminal` 迁移到 `failed`。

## 4. IM-024：通道级重试总预算归属

**裁定：通道级预算归通道侧定义，任务级预算归框架 §4，两者正交不叠加。**

| 预算         | 单位                                                                | 真相源                                                | 耗尽后果                                                        |
| ------------ | ------------------------------------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------- |
| 通道投递预算 | 一次**投递尝试**（`delivery.attempt` / `lastAttempt.attemptCount`） | 本仓 `dispatch-channel.mjs` + `config.circuitBreaker` | `human-escalate`：回滚 `ready` + 持单，**不消耗 `reworkLimit`** |
| 任务返修预算 | 一次**业务返修**（同一 `contextId` 的返修轮次）                     | 框架 §4 + `config.reworkLimit`（2）                   | 死信隔离（INV-08）                                              |

两条判据：

1. **降级路径切换是否计一次重试**：计入 `delivery.attempt`（新通道的首投仍是一次真实投递），但**不计入原通道的连续失败计数**——原通道的失败已由 `fallbackDelivery` 记过一次，重复计数会让熔断被降级动作提前触发。
2. **不把通道预算写成任务预算**：`reworkLimit` 只在验收不通过时递增；通道故障导致的重派不得写进 `attemptCount`，否则一次通道抖动就会吃掉业务返修额度。

## 5. IM-025：熔断阈值与计数维度

**裁定：复用通用熔断平面，通道按「下游实例」计数；不另立通道独立计数。**

| 口径项     | 裁定                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 计数维度   | 按**通道**（`gui-relay` / `gui-file-fallback` / `file`）连续失败次数计数，即框架 §5.1 的「工具 / 下游实例」维度；同一通道跨任务复用同一计数 |
| 阈值参数   | `config.circuitBreaker.consecutiveFailureThreshold`（默认 3）、`cooldownMinutes`（默认 10）；参数由适配层声明，框架不固化数值               |
| 状态位     | `closed` / `open` 已实现；`half-open` 仍为**预留概念位**（本批不实现恢复试探，见 §7 待办）                                                  |
| 可观察性   | 开闸发 `channel-circuit-open` 动作（含 `channel` / `consecutiveFailures` / `threshold`），并写运行态 `entry.channelCircuit`                 |
| 与死信分工 | 熔断拦后续投递（下游平面），死信隔离任务（任务平面），互不替代                                                                              |

## 6. IM-026：失败定性三分法的适用范围

**裁定：framework §4.2 三分法**不豁免**通道层，且定性对象是「投递尝试」而不是「任务」。**

| 定性       | 通道侧判定                                   | 处理                                       |
| ---------- | -------------------------------------------- | ------------------------------------------ |
| 确定性缺陷 | 复现稳定（如登录门始终存在、投递件缺字段）   | `fail-terminal`：任务 `failed`，附 `cause` |
| 偶发波动   | 复现不稳定（进程首次拉起超时、粘贴偶发失败） | 回滚 `ready` 重试，计入连续失败计数        |
| 既有债     | 改动前基线即存在（如 relay 侧已知限制）      | 持单待人工 + 登记改进项，注明基线数字      |

> 与 §3 的关系：三分法决定**怎么处置**，§3 决定**是否改写任务终态**。两者叠加即 `deterministic → failed`，其余 → `ready`。

## 7. IM-027：通道演练的可复核基线

**裁定：结构基线 + 数值基线两层并用，数值当场复核。**

| 层       | 取什么                                                                                                                                    | 何时必查                                                                    |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 结构基线 | 稳定路径清单：`SESSION_PATHS` 三值 + `LOCATE_LAYERS` 枚举 + `confirm` 三件套（`sessionPath` / `locateLayer` / `evidenceRef`）+ 投递件路径 | **每次**演练/投递确认必查（机读，`channel rules` / `channel state` 可复核） |
| 数值基线 | 当日通道成功率快照：`summarizeChannelOutcomes` 的 `attempted` / `dispatched` / `failed` / `successRate`                                   | 每次演练**当场取当次快照**，不得沿用上一轮数字（框架 §4.2 判据）            |

落地：演练记录必须同时给「路径清单比对结论」与「当次成功率快照」两段；缺任一段视为基线不成立。
