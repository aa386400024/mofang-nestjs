# 混合式 BDI 智能体引擎架构蓝图 V1.0

> **路径**：`docs/architecture/hybrid-bdi-agent-blueprint-v1.0.md`

> **创建**：2026-11-05（基于 Coze 下线趋势判断 + 现有 BDI 引擎架构评审 + 12 个边界问题盘点）
> **配套**：[`engine-endstate-blueprint-v1.0.md`](engine-endstate-blueprint-v1.0.md)（北极星终局）、[`ai-engine-roadmap-v1.1.md`](ai-engine-roadmap-v1.1.md)（分阶段路线）

## 0. 一句话定义

**从「规则驱动的 BDI」演进为「LLM 审议 + 状态骨架的混合式 BDI 智能体」**——保留 BDI 三层状态结构作为可控骨架，把状态更新的决策从人工算子换成 LLM 审议，同时加约束层保证可控性、可解释性、可复现性。

不是推倒重来，是把「delta 计算器」从硬编码规则换成 LLM 推理，管道结构完全保留。

---

## 1. 为什么要变（Coze 下线的启示）

### 1.1 行业信号

2026 年 Q4，字节 Coze、Dify、Flowise 等静态工作流编排工具集体收缩/下线。本质原因：

- **静态工作流 = 人工编排节点 + 固定分支 + 硬编码跳转**
- AGI 趋势 = 状态驱动 + 自主规划 + 动态适应
- 人工编排的表达能力天花板，远远低于大模型自身的推理能力
- 结果：用铁链拴着跑车，越优秀的模型越被规则束缚

### 1.2 我们的现状和隐患

现在的 BDI 引擎（`src/engine-core/cognition/`）：

```
state-transition.ts：
  咨询师说"共情" → trust +0.02, resistance -0.03（人工硬编码映射）
  咨询师说"面质" → resistance +0.05, trust -0.01（人工硬编码映射）
  ...
```

**这就是代码版的静态工作流。** 隐患：

1. **维护成本指数级上升**：每加一个角色类型、一种临床场景，就要补一堆算子规则
2. **模型越强越鸡肋**：MiniMax M3 本身就能判断"这句话共情效果好不好"，我们还要用人工规则再算一遍
3. **表达能力天花板低**：人工规则只能覆盖"典型事件→典型反应"，复杂对话（多重情绪交织、微妙的语气变化）覆盖不了

### 1.3 不变就是等死

现在 Phase2 做的这些 WP（同盟三维、人格调节、信念扩展）——都是在**丰富状态结构**，不是在优化决策逻辑。状态越来越复杂，但决策还是那套人工规则。

**状态结构越丰富，人工规则的覆盖缺口就越大。**

## 2. 目标架构：三层分离

```
┌─────────────────────────────────────────────────────┐
│  ③ 约束校验层（保留 + 增强，兜底可控性）              │
│  delta cap / 临床合理性校验 / 意图锁定 / 可复现控制    │
├─────────────────────────────────────────────────────┤
│  ② 审议引擎层（新增，替代人工算子库）                  │
│  LLM 审议：当前状态 + 本轮对话 → 结构化状态变更建议     │
├─────────────────────────────────────────────────────┤
│  ① 状态骨架层（完全保留，engine-core 不动）            │
│  信念 / 欲望 / 意图 / 同盟三维 / 情绪 / 记忆           │
│  纯数据结构，可序列化、可调试、可复现                  │
└─────────────────────────────────────────────────────┘
```

### 2.1 状态骨架层（保留不动）

**是什么**：`src/engine-core/domain/` 下的所有数据结构——信念、欲望、意图、同盟三维、情绪、记忆快照。

**为什么保留**：
- 这是 BDI 的核心价值——结构化的心理状态，可观测、可调试、可教学
- 纯数据结构，可序列化、可落库、可回放
- engine-core 纯层边界不破（零 LLM / 零网络 / 零 prompt）

**变了什么**：什么都没变。状态结构继续丰富（WP57 信念激活、WP49 大五人格这些全部保留）。

### 2.2 审议引擎层（新增）

**是什么**：替代 `cognition/state-transition.ts` 里的人工算子——由 LLM 来判断"这轮对话后，状态应该怎么变"。

**输入**：
- 当前状态快照（结构化 JSON，不是完整对话历史）
- 本轮咨询师发言 + 来访上一轮发言
- 角色基线信息（角色 ID + 依恋类型 + 核心信念摘要）

**输出**：
```json
{
  "deltas": {
    "trust": 0.018,
    "safety": 0.005,
    "resistance": -0.02,
    "emotionValence": -0.01
  },
  "reason": "咨询师语气温和，但未直接回应来访情绪，共情效果中等",
  "operatorTags": ["empathy_partial", "not_affirmative"],
  "intentionShift": null
}
```

**关键设计**：
- LLM 只输出"变更建议"，不直接改状态
- 变更建议要过约束校验层才能生效
- 审议服务在适配层（`src/engine-adapters/deliberation/`），不在 engine-core

### 2.3 约束校验层（保留 + 增强）

**现有保留**：delta cap（每轮变化幅度上限）、边界断言。

**新增增强**：
- **软状态 / 硬安全分层**：
  - ✅ **软状态走 LLM 审议**：trust / safety / bond / resistance / emotionValence / emotionArousal（连续渐变，错一点不致命）
  - ❌ **硬安全走规则兜底**：自杀倾向 / 自伤风险 / 危机等级（二值/三值判断，错了就是事故，永远不经过 LLM）
- **临床合理性校验**：trust 单轮最多 +0.05，阻抗不能从 0.2 跳到 0.9 这类规则
- **意图锁定机制**：当前核心意图在 N 轮内不随意切换
- **可复现控制**：考核模式下锁温度锁 seed，保证逐字可复现
- **高风险状态人工确认**：自杀倾向、危机信号维度的变化，必须人工审核

## 3. 十三个边界问题及应对

> 这些是做之前必须想清楚的坑。按严重程度分三档。

### 3.1 致命级边界（不解决就不能上线）

#### 边界 1：状态一致性与时序竞争

**问题**：LLM 审议耗时 1-3 秒。用户快速连发两条消息时，第二条审议基于的是旧状态（第一条的 delta 还没落库），两个审议同时写状态 → 状态错乱。

**应对**：
- 会话级串行队列：同一个 sessionId 的审议请求排队执行，前一个落库后才能跑下一个
- 审议输入用"最近已提交的快照"，不用内存中间态
- per-session mutex 实现，NestJS 侧加

#### 边界 2：可解释性断层（实训平台命根子）

**问题**：实训平台的核心价值是"学员练完知道哪里错了，督导能复盘每一轮"。规则算子时代可解释（"触发了 empathyBoost 算子 → trust +0.02"），LLM 审议时代呢？为什么是 0.018 不是 0.02？

**应对**：
- 审议输出必须带**理由字段**（自然语言解释为什么这个 delta）
- 审议输出必须带 **operatorTags**（可枚举标签，不是自由文本——这样才能做统计分析）
- 理由 + 标签进 trace 系统，督导复盘时能看到每一轮的审议依据
- 没有可解释性 = 从实训工具退化成陪聊玩具

#### 边界 3：心理数据合规边界

**问题**：LLM 审议要把心理对话内容（甚至创伤倾诉、自杀意念）发给第三方大模型（MiniMax）。触三条监管红线：个保法敏感个人信息、精神卫生法咨询记录、网安法数据安全。

**应对**：
- 用户协议明确写：对话内容会用于 AI 来访的状态推理和实训优化
- 审议 prompt 不传完整用户原文，只传结构化事件分类（"咨询师使用了共情技术"），减少敏感数据暴露
- 高风险对话（涉及自杀、自伤）走本地规则审议，不发给 LLM
- 长期方案：核心审议用自托管小模型，敏感数据不出服务器

#### 边界 4：降级与故障恢复

**问题**：LLM 审议服务挂了 / API 超时，整个会话卡死吗？规则算子时代零依赖永远不挂，切 LLM 后多了一个故障点。

**应对**：三级降级策略
1. 正常模式：LLM 审议
2. 降级 1：LLM 超时 → 用最近一次审议的状态 + 简单规则微调（自然衰减一点）
3. 降级 2：LLM 完全不可用 → 切回规则算子模式（只覆盖核心场景，体验差但能用）
- 降级状态可观测：督导和管理员能看到"这个会话是降级模式跑的"
- 降级模式下的会话不能用来做正式考核

#### 边界 5：软状态 / 硬安全分层（审议边界红线）

**问题**：是不是所有状态维度都可以交给 LLM 审议？自杀倾向、危机等级这种硬安全指标，如果 LLM 判错了（该拦截的没拦截），就是事故。

**应对**：分层处理
- ✅ **软状态走 LLM 审议**：trust / safety / bond / resistance / emotionValence / emotionArousal——这些是连续渐变的心理状态，错一点不致命，LLM 的推理能力比人工规则强
- ❌ **硬安全永远走规则兜底**：自杀倾向 / 自伤风险 / 危机等级——这些是二值/三值判断（低/中/高风险），错了就是事故，永远不经过 LLM
- **原则**：LLM 审议只做"软状态的渐变计算"，硬安全维度永远走规则引擎 + PsyGUARD 探测
- **校验层再拦一道**：即使 LLM 输出了 delta，过约束校验层时如果发现硬安全维度被修改了，直接拒绝并打告警

> 这条是红线，没有商量余地。心理实训平台的合规底线不能交给黑盒模型。

### 3.2 严重级边界（不解决体验会很差）

#### 边界 6：LLM 输出格式漂移

**问题**：让 LLM 输出 JSON delta，今天格式正确，明天可能多了注释、少了字段、用了 markdown 代码块。

**应对**：
- 强制 JSON 模式（MiniMax 支持 `response_format: json_object`）
- 输出 schema 校验层：JSON 解析后过 zod / class-validator，不合法就重试一次
- 重试失败兜底：这一轮 delta 为 0，状态不更新，打告警日志
- 输出字段全是固定枚举或数值范围，没有自由文本空间

#### 边界 7：长对话上下文爆炸

**问题**：审议输入要传状态快照 + 对话上下文 + 角色设定。30 轮下来 prompt 破 10k token，成本和延迟都扛不住。

**应对**：
- 审议输入不是全量传，是**相关维度传**：聊情绪话题就只传情绪/阻抗/同盟，不传信念层
- 角色设定只传一次：存会话上下文里，后续只传"角色ID + 基线版本号"
- 记忆召回结果进审议输入，但只传 Top3 摘要
- 审议频率不是每轮都跑：简单对话每 2-3 轮审议一次，关键节点才每轮审议

#### 边界 8：审议漂移检测

**问题**：LLM 审议是黑盒，可能慢慢把角色带偏——本来是回避型，聊 20 轮后变成主动倾诉了。你以为是正常进展，其实是审议漂了。

**应对**（Phase3 做，PoC 阶段先留接口）：
- 基线偏离告警：每个角色有预设的"正常演化区间"，超出就告警
- 每轮 delta 的统计分布监控：滑动窗口分布突然变宽/变偏就是漂移信号
- 随机抽检：每天抽 1% 的会话人工审核

#### 边界 9：考核公平性与模型版本

**问题**：考核场景用固定模型版本，模型升级后审议行为变了，评分标准跟着变——对上个月考过的学员公平吗？

**应对**（Phase3 做）：
- 考核场景锁模型版本 + 锁 prompt 版本，不自动升级
- 模型升级前跑 100 个标准测试用例，对比新旧版本差异，可接受范围内才升级
- 考核报告里写清楚模型版本和 prompt 版本，可追溯

### 3.3 优化级边界（可以后期迭代）

| 边界 | 问题 | 应对思路 | 什么时候做 |
|---|---|---|---|
| 意图锁定粒度 | 锁多久合适？太短没效果，太长不灵活 | 做成可配置参数，不同角色类型不同 | PoC 阶段做基础版，后期调参 |

## 4. Phase2 PoC 工作包清单（WP63–WP68）

> 这 6 个 WP 是混合式 BDI 的最小可行验证。**不是替换生产，是影子模式并行跑**，用数据证明这条路走得通。

### WP63 · 审议输出 Schema 与可解释性设计

**优先级**：🟡 P1
**预估**：小
**前置依赖**：无

**做什么**：
- 定义审议输出的 JSON schema（deltas + reason + operatorTags + intentionShift）
- operatorTags 枚举表初版（empathy_partial / not_affirmative / confrontation_soft / ...）
- 理由字段进 trace 日志格式
- **审议 prompt 模板设计**：
  - 系统 prompt：角色设定摘要（依恋类型/核心信念）+ 临床约束（不能给建议/不能做诊断）+ 输出格式要求 + operatorTags 枚举表
  - 用户 prompt：当前状态快照（相关维度）+ 本轮对话内容 + 记忆召回 Top3 摘要
  - 双模式分离：考核模式 prompt（温度 0，逐字可复现）vs 自由练习模式 prompt（温度 0.3，有随机性）
  - prompt 版本号管理：和模型版本一样，考核场景要锁 prompt 版本

**为什么先做这个**：schema + prompt 定了，后面 PoC 才有东西可跑。这两个是审议质量的根基。

**边界**：
- engine-core 零改动——schema 和 prompt 都在适配层
- operatorTags 是枚举字符串，不是内核类型
- prompt 里不传完整用户原文，只传结构化事件分类（合规要求）

### WP64 · LLM 审议层 PoC（影子模式）

**优先级**：🟡 P1
**预估**：中
**前置依赖**：WP63

**做什么**：
- 新增 `src/engine-adapters/deliberation/llm-deliberation.service.ts`
- 影子模式运行：每轮对话后同步跑一次 LLM 审议，结果**不生效**（不写入状态）
- 对比数据：LLM 审议的 delta vs 规则算子的 delta，记录差异
- 积累 100 场真实对话后，分析：哪些场景规则准、哪些不准
- **影子模式可观测指标**（这是 PoC 最核心的产出）：
  - 审议耗时 P50 / P95 / P99
  - 审议 token 消耗（输入 + 输出）
  - 审议失败率（格式不合法 / 超时 / API 错误）
  - **审议 delta vs 规则算子 delta 的差异分布**——按维度统计（trust 差多少、resistance 差多少）
  - 差异最大的 Top10 场景——这些就是规则算子覆盖不了、需要 LLM 的地方
- **数据存储**：审议结果 + 对比数据写入专门的 trace 日志表（`deliberation_trace`），字段包括：sessionId、turnIndex、规则算子 delta、LLM 审议 delta、差异值、operatorTags、reason、耗时、token 消耗、成功/失败。方便后续按维度统计分析
- **调用时序**：影子模式阶段，审议与渲染**并行**跑（审议不影响渲染结果，所以不需要等审议完再渲染）。切灰度后改为串行（审议先跑，结果进渲染 prompt）

**PoC 验收标准**（100 场对话跑完后，满足以下条件才进 Phase3A）：
- 审议成功率 > 95%（格式合法 + API 不报错）
- 审议耗时 P95 < 3s（不拖慢会话）
- delta 差异分布在可接受范围：软状态维度差异均值 < 0.01（即 LLM 和规则的判断基本一致，差异不是系统性偏差）
- 差异最大的 Top10 场景有临床合理性（人工抽样 5 场，督导认可"LLM 的判断更接近真实临床反应"）
- 高安全维度零误触发（LLM 没有输出过硬安全维度的 delta）

**为什么影子模式**：不影响生产，先验证 LLM 审议的输出质量。没有可观测指标，100 场对话跑完你也不知道到底好不好。

**env 配置项**（.env.example 新增）：
- `ENGINE_DELIBERATION_ENABLED` —— `true` / `false`，默认 `false`（影子模式开关）
- `ENGINE_DELIBERATION_MODEL` —— 审议用的模型名，默认用现有 MiniMax Flash
- `ENGINE_DELIBERATION_TIMEOUT_MS` —— 审议超时时间，默认 3000
- `ENGINE_DELIBERATION_TEMPERATURE` —— 审议温度，默认 0.3（自由练习模式）

**边界**：
- engine-core 零改动
- 生产状态更新仍然走规则算子，审议只是旁路观察
- 审议结果只写日志表，不影响任何线上行为
- 高安全维度（自杀倾向/危机等级）不跑 LLM 审议，只走规则

### WP65 · 会话级串行队列与状态一致性

**优先级**：🔴 P0
**预估**：小
**前置依赖**：WP64

**做什么**：
- 同一个 sessionId 的审议请求排队执行（per-session mutex）
- 状态快照版本号机制：审议输入用"最近已提交的快照版本"，不用中间态
- 防止并发写覆盖导致状态错乱

**为什么 P0**：这是上线前必须解决的硬约束，不解决就不能切流量。

### WP66 · 审议输出格式校验与重试

**优先级**：🟡 P1
**预估**：小
**前置依赖**：WP63

**做什么**：
- JSON 解析 + zod schema 校验
- 格式不合法自动重试一次（带修正提示）
- 重试仍失败 → 本轮 delta = 0，打告警日志，不阻断对话
- 强制 `response_format: json_object`

### WP67 · 三级降级策略

**优先级**：🟡 P1
**预估**：小
**前置依赖**：WP64

**做什么**：
- 降级 1：LLM 审议超时（>3s）→ 跳过审议，状态不变
- 降级 2：LLM 服务连续失败 → 切回纯规则算子模式
- 降级状态标记：会话打标 `degraded: true`，不能用于正式考核
- 降级事件写日志 + 告警

### WP68 · 意图锁定机制（基础版）

**优先级**：🟢 P2
**预估**：小
**前置依赖**：无

**做什么**：
- 当前意图加一个 `lockedUntilRound` 字段
- 锁定期间，审议输出的 intentionShift 被忽略（除非有明确触发事件）
- 触发事件白名单：咨询师直接提问了这个意图相关的话题
- 锁定轮数做成可配置参数（默认 3 轮，工程种子值待校准）

**为什么 P2**：影子模式阶段不需要，切灰度前做就行。

## 5. 与现有架构的关系

### 5.1 什么保留、什么变、什么新增

| 层 | 现状 | 未来 | 变了什么 |
|---|---|---|---|
| 状态骨架（domain/） | BDI 三层 + 同盟三维 + 记忆 | 完全保留，继续丰富 | 不变 |
| 决策逻辑（cognition/） | 人工规则算子 | LLM 审议 + 规则兜底 | **核心变化** |
| 约束校验 | delta cap | delta cap + 临床合理性 + 意图锁定 | 增强 |
| 渲染层 | RenderSpec → LLM 口语化 | 完全保留 | 不变 |
| 记忆系统 | 三级记忆 + 召回策略 | 完全保留 | 不变 |
| engine-core 纯层边界 | 零 LLM / 零网络 / 零 prompt | 完全保留 | 不破 |

### 5.2 engine-core 边界破不破？

**不破。**

- LLM 审议在适配层（`src/engine-adapters/deliberation/`）
- engine-core 仍然是纯函数 + 纯数据结构
- boundary.spec.ts 的 11 条断言一条都不用改
- delta 仍然是"过 cap → 落状态"，只是 delta 的计算方式从人工规则变成了 LLM

### 5.3 Phase2 正在做的 WP 白做了吗？

**没有，全部保留。**

WP50 渲染层接入同盟三维 ✅（状态结构更丰富了）
WP57 BDI 信念层深度扩展 ✅（信念激活强度是状态字段，LLM 审议会用到它）
WP59 记忆召回策略统一 ✅（召回策略是审议的输入）
WP49 大五人格字段落地 ✅（人格特质是审议的上下文）

**所有"丰富状态结构"的 WP 都不白做。** 变的只是"状态怎么更新"，不是"状态长什么样"。

## 6. 演进路线

```
Phase 2.5（现在 → 3 个月）：影子模式验证期
  ├─ WP63 审议 Schema 设计
  ├─ WP64 LLM 审议 PoC（影子模式，不影响生产）
  ├─ WP65 会话串行队列
  ├─ WP66 输出格式校验
  ├─ WP67 三级降级策略
  └─ 积累 100+ 场真实对话数据，验证 LLM 审议质量

Phase 3A（3-6 个月）：灰度切换期
  ├─ 规则算子不够用的场景（新角色、复杂对话）→ 切 LLM 审议
  ├─ 伦理盲盒、标准化考核 → 继续用规则（保证可复现）
  ├─ 两种模式可配置切换，不硬切
  └─ WP68 意图锁定机制上线

Phase 3B（6-12 个月）：混合优化期
  ├─ 大部分场景用 LLM 审议
  ├─ 规则算子只保留核心兜底（危机、伦理红线）
  ├─ 审议漂移检测、模型版本管理上线
  └─ 成本优化（分层调度、审议频率调优）
```

## 7. 红线提醒

1. **engine-core 纯层一行不动**——审议在适配层，不在内核
2. **生产不依赖审议**——影子模式阶段，审议挂了不影响任何线上行为
3. **可解释性是硬要求**——没有 reason + operatorTags 的审议输出，不允许上线
4. **可复现性是实训平台命根子**——考核场景必须能锁版本、锁温度、逐字复现
5. **心理数据合规**——高风险对话不发 LLM，走本地规则
6. **高安全维度永远走规则**——自杀倾向 / 自伤风险 / 危机等级，永远不经过 LLM 审议，这是合规底线，没有商量余地
