## 0. 摘要

**形态定位**：Supervisor（编排者）模式的双 agent 系统。任务模型、工件模型、状态机、验收口径按业界标准（对齐 A2A 任务概念与 MCP 工具边界）设计；实现层用文件 + 轻量 JSON 状态索引，不引入协议栈、编排框架或独立服务。

**三条取舍原则**：

1. **模型先行，传输后置**：任务 / 工件 / 状态的 schema 一开始就按标准定义；A2A、MCP、编排引擎是以后的"传输层升级"，模型不动、不返工。
2. **标准件现在落地，重组件预留**：契约、状态外置、工件留痕、验收五类、可靠性规则、审计链这些低成本高收益件现在就做；协议互通、并行调度、独立 agent 池、持久化工作流留扩展点。
3. **单队列起步，切片可并行**：当前单任务队列 + 域切片隔离；任务模型与依赖关系按并行设计，未来放开并发时只改调度，不改契约。

**结论**：这套形态既不落伍（概念、字段、状态机、工件 provenance 与标准架构一一对应），也不过度工程（无额外运行时、无协议适配成本）；规模增长时沿 §12 路线逐层升级。

## 1. 设计取舍对照

| 维度     | 目标态标准                            | 当前形态选择                              | 理由                                                 |
| -------- | ------------------------------------- | ----------------------------------------- | ---------------------------------------------------- |
| 编排模式 | Supervisor + 可选 Team                | Supervisor 双 agent                       | 无长周期常驻角色需求                                 |
| 代理协议 | A2A Task / Message / Artifact         | 采用 A2A 概念与字段，文件承载             | 执行端未开放标准端点；模型对齐即可低成本映射         |
| 工具协议 | MCP Tools / Resources / Prompts       | 命令行 + pnpm；预留 MCP 工具清单与 schema | 当前工具面小，封装 server 的收益未到                 |
| 状态存储 | 持久化 State Store（DB / 工作流引擎） | JSON 状态索引 + 文件工件                  | 任务量在文件可维护范围；接口抽象预留                 |
| 验收角色 | 独立 Reviewer agent                   | 主控兼任，走独立证据核对流程              | 无第二个 agent；核对基于工件与抽跑，不接受执行侧自述 |
| 调度     | DAG + 并行 worker                     | 单队列 + claim 锁 + 依赖标注              | 避免同文件冲突；依赖关系先入模型                     |
| 评估     | 回归集 + golden trace + 指标趋势      | 闸门证据 + 验收记录；指标位预留           | 先积累标准样例，评估体系随批次沉淀                   |

## 3. 角色模型

| 角色                      | 职责                                                                                             | 边界                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| **Human**                 | 目标与方向；策略 / 红线例外批准；技术路线选型；跨任务架构变更；验收分歧仲裁；git push 决定       | 不实现工作单元                                     |
| **Orchestrator**          | backlog 维护；任务拆解与切片；优先级与依赖；派发；claim 管理；验收组织；归档与索引回写；升级判定 | 不写业务实现；不扩任务范围                         |
| **Executor**              | 按任务契约实现；内循环自测；收尾闸门；写交付记录与偏差表；按约定回执                             | 不扩范围；不改策略边界；不新增依赖；不自动提交推送 |
| **Reviewer（兼任）**      | 落地 / 证据 / 范围 / 契约 / 遗留五类核对；关键闸门抽跑；三态结论                                 | 验收阶段不改代码；新问题另开任务                   |
| _Researcher（预留）_      | 取证、调研、方案比选、离线分析                                                                   | 不直接改业务代码                                   |
| _Critic / Tester（预留）_ | 对抗审查、边界与负向用例、回归复核                                                               | 不承担实现                                         |

**角色隔离要求**：Executor 与验收视角必须分离。兼任时，验收结论只能基于工件证据与抽跑复现，不能引用执行侧"已通过"的自述。

## 4. 任务与工件标准模型

### 4.1 概念映射（对齐 A2A，文件承载）

| 标准概念   | 当前形态载体                        | 说明                                         |
| ---------- | ----------------------------------- | -------------------------------------------- |
| Agent Card | 角色能力声明（文档 / 配置）         | 各角色的能力、工具集、边界；预留为结构化声明 |
| Task       | 任务单（pending / completed 内 md） | 唯一 taskId，有状态，走生命周期              |
| Message    | 任务简报、提问、状态说明            | 经会话传递；正式事实以任务单 / 工件为准      |
| Part       | 文本、文件引用、结构化数据          | 回执内变更清单 / 闸门结果用结构化字段        |
| Artifact   | 交付记录、spec、报告、代码变更集    | 落工件存储，回传轻量引用                     |
| contextId  | 批次 / 变更归组标识                 | 同一主题多任务归组；返修新任务沿用 contextId |

### 4.2 任务单字段（frontmatter + 正文）

```yaml
---
taskId: TD-21 # 唯一标识
contextId: phase2.5-c2-ports # 归组标识
type: repository-port # 任务类型
status: ready # 见 §6 状态机
baselineRef: 2b03756 # 版本锚点（commit ref）
dependsOn: [TD-20] # 上游任务
policyRefs: [conventions.md#1.1, conventions.md#1.3] # 引用策略规则
createdAt: 2026-11-15
---
```

正文标准字段组（沿用现有任务单八节结构，对应标准契约）：

| 字段组     | 内容                                               |
| ---------- | -------------------------------------------------- |
| 目标与验收 | objective、successCriteria、outOfScope             |
| 上下文     | references、priorTasks、constraints                |
| 切片范围   | scope（文件 / 模块 / 实体 / 接口清单）、exclusions |
| 交付物     | artifacts 清单、落点路径                           |
| 质量门禁   | gates（命令 / 检查 / 阈值）、evidenceFormat        |
| 风险与升级 | policyRefs、escalationTriggers                     |

### 4.3 回执 / 交付记录字段

| 字段组 | 字段                                                                    |
| ------ | ----------------------------------------------------------------------- |
| 落地   | changedFiles（added / modified / deleted）、artifactRefs                |
| 证据   | gateResults（命令、exit、error / warning、用例数 / 文件数）、reproNotes |
| 范围   | scopeCheck、parallelArtifactsExcluded、noOutscopeRefactor               |
| 契约   | contractChecks、contractRef、fieldAlignment                             |
| 遗留   | backlogItems、openQuestions、manualReviewList                           |
| 偏差   | deviationTable（任务单写法 / 代码现实 / 处理 / 理由）                   |
| 结论   | finalStatus、reviewVerdict、verdictRationale                            |

### 4.4 工件 Provenance（来源追溯）

每个交付工件记录：产出角色、taskId、contextId、baselineRef、时间戳、输入工件引用、工具调用链摘要。保证结论可回溯到源头与版本基线。

### 4.5 工件版本与不可变

- 已交付工件不原地修改；修订产生新版本或新任务；
- 代码经版本控制系统分组提交，提交信息关联 taskId；
- 历史交付记录只读；归档不删除链接。

## 5. 目录与状态存储

### 5.1 目录约定（沿用现有结构，标准化职责）

| 目录                              | 职责                                       | 状态         |
| --------------------------------- | ------------------------------------------ | ------------ |
| `docs/worklog/pending/`           | ready / claimed / working 任务单；回执原文 | 现有         |
| `docs/worklog/pending/archive/`   | 历史回执、中间产物归档                     | 现有         |
| `docs/worklog/completed/<phase>/` | 任务单 + 交付记录成对归档                  | 现有         |
| `docs/team/`                      | 规范活文档、台账、策略规则、任务模板       | 现有         |
| 状态索引（§5.2）                  | 全部任务的状态、claim、依赖、工件指针      | **本次固化** |

### 5.2 状态索引（轻量 State Store）

单一 JSON 文件记录所有任务的运行状态，作为崩溃恢复与调度依据；工件正文仍在文件，索引只存指针与状态。

```json
{
  "version": "1.0",
  "tasks": [
    {
      "taskId": "TD-21",
      "contextId": "phase2.5-c2-ports",
      "type": "repository-port",
      "title": "counselor 域金句子族仓储端口化",
      "status": "working",
      "agent": "minimax-code",
      "baselineRef": "2b03756",
      "dependsOn": ["TD-20"],
      "policyRefs": ["conventions.md#1.1", "conventions.md#1.3"],
      "createdAt": "2026-11-15T12:05:00+08:00",
      "claimedAt": "2026-11-15T12:06:00+08:00",
      "deadline": "2026-11-15T15:04:49+08:00",
      "artifacts": {
        "taskSheet": "docs/worklog/pending/td21-....md",
        "deliveryRecord": null,
        "reply": null
      },
      "verdict": null,
      "history": [
        { "at": "2026-11-15T12:05:00+08:00", "from": "ready", "to": "claimed", "by": "orchestrator" },
        { "at": "2026-11-15T12:06:00+08:00", "from": "claimed", "to": "working", "by": "executor" }
      ]
    }
  ]
}
```

**索引规则**：

- 状态迁移必须追加 `history` 记录（时间、from、to、by）；
- 工件路径只存指针，不复制正文；
- 索引格式为开放 JSON，未来迁 DB 时字段一一对应；
- 索引本身纳入 git 或定期备份，保证崩溃后可重建。

### 5.3 状态存储接口抽象

编排层只通过统一接口读写状态（`getTask` / `updateStatus` / `listByStatus` / `claim` / `release`）；当前实现为 JSON 文件，未来可替换为 DB 或编排引擎，任务模型与上层流程不变。

## 6. 任务状态机

### 6.1 状态枚举（标准子集）

| 状态             | 类型     | 含义                                 |
| ---------------- | -------- | ------------------------------------ |
| `backlog`        | 编排前置 | 台账待办，契约未补齐                 |
| `ready`          | 编排前置 | 契约齐全、基线明确、依赖满足         |
| `submitted`      | 活跃     | 任务已提交给执行端并确认             |
| `working`        | 活跃     | 执行中                               |
| `input-required` | 中断     | 需要补充输入 / 决策                  |
| `completed`      | 终态     | 验收通过（含有条件通过，遗留已登记） |
| `failed`         | 终态     | 错误结束，附原因                     |
| `canceled`       | 终态     | 完成前取消，释放资源                 |
| `rejected`       | 终态     | 验收打回；返修新开任务               |

> `auth-required` 在当前双 agent 本地形态不使用；状态枚举保留，未来接入需要认证的外部 agent 时启用。

### 6.2 迁移路径

```
backlog ──► ready ──► submitted ──► working ──► submitted(回执) ──► review ──► completed
                ▲            │           │                          │
                │            └──► input-required ──► working         ├─ rejected ──► ready（返修新任务，沿用 contextId）
                │            │                                        └─ failed
                └────────────┴──────────────────────────────── canceled
```

### 6.3 状态规则

- **终态不可变**：`completed / failed / canceled / rejected` 不重启；细化与返修在同一 `contextId` 下发起新任务；
- **有效迁移**：不允许终态回到活跃态；`input-required` 解除后回到 `working`；
- **依赖解锁**：上游 `completed` 才解锁下游；
- **版本锚点**：任务记录开工基线；验收核对未基于过期基线；
- **中断可追溯**：`input-required` 记录等待项与触发原因。

## 7. 队列、调度与并发

| 机制     | 当前规则                                        | 并行预留                                   |
| -------- | ----------------------------------------------- | ------------------------------------------ |
| 队列     | 单任务队列；ready 任务按优先级 + 依赖排序       | 多 worker 时按域 / 文件切片分派            |
| Claim 锁 | 领取写入 `claimedAt` 与执行者；租约到点自动释放 | 锁粒度为任务；并行时叠加文件切片不重叠校验 |
| 超时     | 任务级 deadline；超时标记中断 / 失败并释放资源  | 工具级超时预留                             |
| 依赖     | `dependsOn` 标注；上游完成解锁下游              | DAG 并行展开                               |
| 冲突检查 | 交付前 `git diff --name-only` 核对变更集        | 并行任务切片预检                           |
| 背压     | 并发度受执行环境容量约束；超限排队              | 队列长度与 worker 容量指标预留             |

## 8. 工具层：现状与 MCP 扩展点

### 8.1 当前工具集

仓库读写、构建 / 测试（pnpm）、版本控制（git）、代码检索；命令规范以仓库 `package.json` 与 `conventions.md` §1.3 为准。

### 8.2 预留的 MCP 接口

未来将工具封装为 MCP server 时，每个工具声明：输入 schema、输出 schema、副作用类型（只读 / 受限写 / 敏感操作）、所需权限。交接面（任务单 / 工件 / 状态索引）不变，仅工具调用从命令行变为标准原语。

**工具边界（现在即遵守）**：

- 不向业务层暴露底层连接句柄、通用仓储代理、原始查询选项或操作符；
- 工具服务端收口权限校验与调用审计；
- 敏感操作（提交、发布、外部写入）需审批节点；
- Secrets 不进入任务文本、回执或工件。

## 9. 上下文、记忆与恢复

### 9.1 上下文边界

- 执行 agent 获得独立、最小化上下文：任务契约 + 必要引用 + 分配工具；
- 内部推理与草稿不跨代理传播；对外只给契约字段与工件引用；
- 跨任务事实从规范活文档、台账、工件读取，不假设会话记忆延续。

### 9.2 记忆分层

| 层       | 内容                       | 载体                           |
| -------- | -------------------------- | ------------------------------ |
| 工作记忆 | 当前任务中间状态           | 任务上下文 + 状态索引          |
| 共享记忆 | 已确立口径、模块事实、约定 | 规范活文档 + 台账（受控写入）  |
| 工件记忆 | 交付物、报告、规格、代码   | completed 工件库（不可变版本） |
| 长期案例 | 历史决策、经验教训         | 案例库（预留）                 |

### 9.3 崩溃恢复

agent 会话重置后，依 taskId 从状态索引读状态、从工件与规范文档读事实，在新会话重建上下文；恢复不依赖对话历史。

## 10. 验收与质量门禁

### 10.1 五类核对（Reviewer 流程）

1. **落地**：预期工件逐条存在且非空；变更清单与契约比对；临时产物未混入；
2. **证据**：闸门命令、退出码、数字齐全且可复现；关键路径抽跑；失败定性（确定性缺陷 / flake）；
3. **范围隔离**：改动落在授权切片；策略边界未碰；并行产物未混入；无相邻重构；
4. **契约口径**：schema 与字段对齐；真相源唯一；消费端不复算口径；版本随数据下发；
5. **遗留登记**：既有债入 backlog；未决项与人工复核清单完整；索引与归档完成。

### 10.2 三级闸门

| 层       | 时机       | 内容                                                                              |
| -------- | ---------- | --------------------------------------------------------------------------------- |
| 内循环   | 改动中高频 | 定向 spec、lint（缓存）、单文件类型检查                                           |
| 收尾闸门 | 交付前一次 | 根 tsc、build tsc、lint、lint:fast、定向域 spec、全量、边界断言、engine-core diff |
| 边界闸门 | 全程       | AST 级边界测试；红线 diff 为空或例外批准                                          |

### 10.3 结论分级

- **通过**：五项全清 → `completed`；
- **有条件通过**：主体合格，遗留显式登记且不阻塞 → `completed`，遗留入 backlog；
- **打回**：落地缺口 / 证据不实 / 越界 / 契约未对齐 → `rejected`，写明原因与待补动作；返修新开任务。

### 10.4 评估预留

随批次沉淀：标准样例集、golden 执行轨迹、任务通过率 / 返修率 / 耗时 / 工具失败率指标；当前先在交付记录与台账留数字，评估体系待样例积累后独立成平面。

## 11. 可靠性规则

| 机制       | 当前规则                                                         |
| ---------- | ---------------------------------------------------------------- |
| 幂等       | taskId + 工件版本保证重复执行不产生重复副作用                    |
| 重试       | 可恢复错误限次重试；不可恢复错误直接 `failed`                    |
| 超时       | 任务级 deadline；超时释放 claim 与资源                           |
| 失败定性   | 单跑复现区分确定性缺陷与偶发 flake；既有债基线与新增改动分开记录 |
| 死信       | 反复失败任务入 blocked / backlog，附完整错误上下文，转人工       |
| 版本锚点   | 基线 ref 入任务与工件 provenance                                 |
| 不可变任务 | 终态不重启；返修新开任务                                         |

## 12. 演进路线（模型不变，传输层升级）

| 阶段              | 触发条件                                          | 升级内容                                                           | 不变项                          |
| ----------------- | ------------------------------------------------- | ------------------------------------------------------------------ | ------------------------------- |
| **L0 当前**       | 双 agent、单队列、文件交接                        | 文件 + JSON 状态索引 + 标准任务 / 工件 schema                      | —                               |
| **L1 工具标准化** | 命令行交接出现重复解析 / 权限边界不清             | 本地 MCP server 封装仓库 / 测试 / git / 检索                       | 任务模型、工件、目录约定        |
| **L2 状态持久化** | 任务量 / 并发超出文件索引上限，或需多会话共享状态 | 状态索引迁 DB；可引入编排框架承接状态机与重试                      | 任务 schema、状态枚举、工件模型 |
| **L3 代理协议化** | 出现第二个稳定执行 agent，或跨机器 / 跨系统协作   | 接入 A2A：Agent Card + Task + Message + Artifact；现有字段直接映射 | 契约内容、验收流程、工件标准    |

**演进原则**：协议与框架是传输层；任务模型、状态机、工件 schema 在 L0 即按标准定义，后续升级只换承载，不返工业务契约。

## 13. 人机边界与升级

### 13.1 自动决策（Orchestrator 按规则执行）

backlog 内批次排序；就绪判定；模板化派发；格式与契约校验；归档与索引回写；超时释放 claim；限次重试；回执归档。

### 13.2 必须人工决策

方向与目标；红线 / 策略例外；技术路线选型；跨任务架构变更；验收分歧；对外发布与 push。

### 13.3 升级触发

| 条件                      | 动作                               |
| ------------------------- | ---------------------------------- |
| 触及红线 / 策略边界       | 暂停执行，转人裁决                 |
| 同一任务失败 / 打回达限次 | 升级人工，附失败证据与可选路径     |
| 契约冲突且无先例可依      | 暂停，取证后回写契约，必要时人拍板 |
| 需要外部输入 / 授权       | `input-required` 中断              |
| 发布 / 外部系统写入       | 审批节点                           |

升级消息携带：taskId、contextId、当前状态、已尝试路径、失败证据、可选方案、建议决策点。

## 15. 第一批落地清单（低成本高收益）

1. **状态索引文件**：按 §5.2 结构建立，回填在跑与历史任务的 taskId / 状态 / 基线 / 工件指针；
2. **任务单 frontmatter**：taskId、contextId、type、status、baselineRef、dependsOn、policyRefs 固化进任务模板；
3. **回执模板字段**：§4.3 七组字段并入交付记录模板；
4. **验收脚本化项**：文件存在性、git diff 范围、闸门退出码与用例数核对；语义判断仍走人工 / 主控；
5. **claim 与超时**：状态索引记录 claim 时间与 deadline；轮询超时自动释放；
6. **审计链**：taskId 贯穿任务单、回执、提交信息、台账更新记录；
7. **策略引用**：任务单 `policyRefs` 指向规范活文档锚点，验收时逐条核对。
