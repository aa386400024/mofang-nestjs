# 语料与内核版本漂移取证 v1.0

- 日期：2026-11-24
- 出处：AF-428（复核 AF-427 表三「实测/系数比」的可信度）
- 数据源：`data/debug-sessions` 13 场 / 205 轮；内核 `src/engine-core/cognition/state-transition.ts` 的 `DELTA_TABLE`
- 性质：只读取证，不改语料、不改内核、不重跑会话

## 一、结论先行

**13 场语料不是同一版内核产出的快照，而是跨版本攒起来的混合体。** 同一个算子、同一类「单算子轮」，在语料里出现了多套不同的 delta 签名。

最直接的证据是 `empathy`：单算子轮共 31 轮，签名分五簇，其中最大一簇 24 轮的 `safety` delta 是 **0.014**，而当前内核表写的是 **0.060**；另有一簇 2 轮是 **0.020**（AF-315 把 safety 从 0.02 提到 0.06 之前的旧值）。

因此 AF-427 表三的「实测/系数比」只能回答「语料生成时那条链路是否把系数原样落地」，**不能回答「当前系数是否生效」**。

## 三、能读出的三件事

1. **破坏性算子（judgment / preaching / minimizing / sensitive_touch）与 neutral 全部与当前表逐字一致**，说明这些轮次产出于当前系数版本之后。
2. **正向修复算子（empathy / acceptance / open_probe）几乎全部不一致**，且不一致的方式不止一种：既有「旧值」（safety 0.014 / 0.020），也有「被调制值」（verbal −0.023077 这类非整比数字）。后者不是表值本身，说明当时链路里还叠了一层系数调制。
3. **同一算子内部也不一致**：empathy 31 轮里 24 轮一套、3 轮一套、2 轮一套、单轮各一套。语料是按「会话」为单位攒的，一个会话内可能跨版本，所以不能按会话整体打版本标签。

## 四、处置建议

1. **表三的使用边界**：`实测/系数比` 只用于「同一算子内部的相对稳定性」判断（比如四个破坏性算子都是 100%，说明那条链路没有二次调制、没有 cap 截断）；不用于「当前系数是否达到设计幅度」的判断。
2. **要谈当前系数，必须重跑语料**：一次全新批次（同一内核版本、同一 env）才能给出有效口径。建议在补语料任务里同时记录 `kernelRef` / `deltaTableHash`，让每批语料自带版本指纹。
3. **不要按会话整体标版本**：本次取证已证明跨簇，按会话标注会产生错标签。
4. **台账维护**：AF-427 台账表三的结论段落需补一行引用本取证，说明 88.0% 的差额主要来自版本漂移，而不是落笔时的「AllianceConfig 覆写」猜想（后者在破坏性算子上 100% 一致的证据下不成立）。

## 五、复算

签名分簇可复现：对每个 trace 取 `deltaDetail.events` 长度恰为 1 的记录，按 8 维系数序列做键聚合计数。AF-427 脚本的 `--json` 输出里 `corpus.byOperator.<kind>.realizedSingleMean` 即该簇的均值口径。
