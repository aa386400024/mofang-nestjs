## 0. 摘要

**目标**：构建一个可扩展的多 agent 工程系统——人设定方向与策略边界，编排层拆解与调度，专职 agent 在受控上下文内执行，工件与状态外置可审计，验收与评估作为独立平面把关；系统在 agent 崩溃、会话重置、工具故障后可从持久化状态与工件完整恢复。

**核心架构决策**：

1. **编排模式**：以 **Orchestrator-Subagent（编排者-子代理层级）** 为主；需要跨调用保持领域上下文的长周期角色采用 **Agent Team（共享任务队列 + 邮箱）** 模式；不采用对等自治网络。
2. **协议分层**：工具接入走 **MCP**（agent → 工具）；agent 委托与状态回传走 **A2A**（agent → agent）；任务、消息、工件、状态以标准模型表达。
3. **工件外置**：agent 产出直接写入工件存储，回传轻量引用，不经对话历史复制，避免多阶段信息衰减（"传话游戏"）与 token 膨胀。
4. **任务不可变**：每个任务是清晰、不可变的工作单元；进入终态后不重启，细化与跟进在同一上下文分组下新开任务。
5. **验收与评估独立成平面**：机器可判项自动核对，语义与策略判断由独立验收角色执行；质量门禁、回归评估、可观测性横切于所有 agent。
6. **安全与人在环是默认项**：工具权限分级、策略机读化、敏感动作审批节点、显式升级条件，均为架构内置而非事后补丁。

## 1. 设计原则

| #   | 原则               | 含义                                                                             |
| --- | ------------------ | -------------------------------------------------------------------------------- |
| P1  | 关注点分离         | 编排、执行、验收、工具、状态、工件、观测、安全各自独立组件，单向依赖，不越层调用 |
| P2  | 契约先行           | 任务、消息、工件、状态均有显式 schema；agent 仅凭契约即可工作，不依赖会话记忆    |
| P3  | 状态外置           | 任务状态、共享记忆、工件持久化在 agent 进程之外；agent 可随时销毁重建            |
| P4  | 上下文隔离         | 每个子代理独立上下文；跨代理只传契约字段与工件引用，不泄漏内部推理               |
| P5  | 证据可复现         | 所有质量结论附命令、退出码、数字与工件路径；结论可由第三方重新跑出来             |
| P6  | 失败显式化         | 错误、超时、降级、打回都是一等公民状态，不靠静默跳过或默认成功                   |
| P7  | 最小权限           | agent 与工具按角色授予最小权限；敏感动作经审批；默认拒绝未声明能力               |
| P8  | 可审计可回放       | 关联 ID 贯穿任务、消息、工件、提交与日志；历史路径可追溯、可回放                 |
| P9  | 标准优先、厂商中立 | 协议与数据模型采用开放标准；框架选型可替换，不绑定单一 SDK 生态                  |

### 2.1 组件职责

| 层       | 组件                   | 职责                                                                       | 不做什么               |
| -------- | ---------------------- | -------------------------------------------------------------------------- | ---------------------- |
| 接入层   | Human                  | 目标与方向、策略边界、敏感动作审批、跨任务分歧仲裁、最终发布决定           | 不实现具体工作单元     |
| 接入层   | 外部系统               | 通过标准接口提交任务、订阅事件                                             | 不直接访问内部工具     |
| 编排层   | Router                 | 按任务类型与能力把请求路由到对应专职 agent                                 | 不做业务实现           |
| 编排层   | Planner                | 目标拆解为任务 DAG、定义验收标准、识别依赖与风险                           | 不跳过契约直接派发     |
| 编排层   | Supervisor             | 调度、状态推进、结果综合、升级判定；可嵌套（子团队只对子团队 leader 暴露） | 不扩任务范围           |
| 编排层   | Task Queue / Scheduler | 排队、并发控制、claim 分配、超时与重试调度                                 | 不执行业务逻辑         |
| 编排层   | State Store 接口       | 任务与运行状态的持久化抽象（实现可换 DB / 文件 / 工作流引擎）              | 不存业务工件正文       |
| Agent 池 | Executor               | 按任务契约实现；内循环自测；产出工件与交付记录                             | 不扩范围、不改策略边界 |
| Agent 池 | Reviewer               | 独立验收：落地、证据、范围、契约、遗留；给分级结论                         | 不在验收中改代码       |
| Agent 池 | Researcher             | 取证、调研、方案比选、离线分析                                             | 不直接改业务代码       |
| Agent 池 | Critic / Tester        | 对抗性审查、边界与负向用例、回归复核                                       | 不承担实现职责         |
| 工件层   | Artifact Store         | 产物持久化、版本、provenance、检索                                         | 不解释产物语义         |
| 工件层   | Memory Store           | 分层记忆：任务内工作记忆、跨任务共享记忆、长期案例库                       | 不存放敏感对话原文     |
| 工具层   | MCP Server             | 以标准原语暴露工具 / 资源 / 提示；权限与审计在服务端收口                   | 不内嵌业务决策         |
| 横切     | Observability & Eval   | trace、指标、日志、评估回归集、质量门禁                                    | —                      |
| 横切     | Security & Policy      | 权限、策略规则、secrets、注入防护、审计日志                                | —                      |
| 横切     | Reliability            | 幂等、重试、退避、超时、断路器、死信、崩溃恢复                             | —                      |

## 3. 编排模式选型

### 3.1 业界五种模式对照

| 模式                      | 结构                                                                  | 适用                                               | 局限                                         |
| ------------------------- | --------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------- |
| **Orchestrator-Subagent** | 一个编排者规划、委派、综合；子代理单次有界调用后返回                  | 子任务短、聚焦、产出清晰；并行分面探索             | 子代理不跨调用保留状态；长周期领域熟悉度不足 |
| **Agent Team**            | 协调者 + 多个常驻 worker；共享任务队列与邮箱；worker 跨调用保持上下文 | 需要持续领域熟悉度的长周期工作（如迁移、专项模块） | 上下文管理与一致性成本更高                   |
| **Pipeline**              | 角色按固定阶段串联                                                    | 流程稳定、可流水线批量生产                         | 返工路径长；不适合探索性任务                 |
| **Peer Network**          | agent 对等互派，无中心                                                | 多组织、跨边界协作                                 | 无共享状态；冲突归因与审计困难               |
| **Blackboard**            | 共享工作区 + 多个agent 按规则读写                                     | 知识汇聚、多视角拼合                               | 调度规则复杂；并发写冲突需专门控制           |

### 3.2 目标态选型

- **主模式：Orchestrator-Subagent**。责任链清晰、状态集中、崩溃易恢复、契约统一；多数实现与审查任务为短周期有界调用。
- **辅助模式：Agent Team**。对需要跨多次调用积累模块上下文的专职角色（如某一域的长期维护 agent），采用共享 Task List + Mailbox，worker 保留私有上下文。
- **不采用：Peer Network**。跨厂商 agent 无共享记忆与状态，对等委托的冲突仲裁、审计归因、版本一致性成本过高，与最小权限和可审计原则冲突。
- **可嵌套**：Supervisor 之下可有子团队；上层只与子团队 leader 交互，不感知内部进一步委派。

### 3.3 模式选择判据

| 判据       | 选 Subagent        | 选 Team                    |
| ---------- | ------------------ | -------------------------- |
| 任务周期   | 单次有界调用内完成 | 跨多次调用、多轮迭代       |
| 上下文需求 | 仅需任务契约       | 需积累模块 / 领域历史      |
| 并行性     | 可按面并行分发     | 分工协作、互有依赖         |
| 状态持续性 | 无跨调用状态       | 需在 worker 侧保留工作记忆 |

## 4. 标准任务模型（对齐 A2A）

### 4.1 核心概念

| 概念                     | 定义                                                                | 本系统对应                                |
| ------------------------ | ------------------------------------------------------------------- | ----------------------------------------- |
| **Agent Card**           | 描述 agent 身份、能力、技能、服务端点与认证要求的元数据文档         | 每个专职 agent 的能力声明；编排层据此路由 |
| **Task**                 | 委托的基本工作单元，唯一 ID，有状态，走定义好的生命周期             | 一个交付单元（实现单、评审单、取证单）    |
| **Message**              | 客户端与 agent 之间的一轮通信，含 `role`（user / agent）与若干 Part | 任务简报、提问、状态说明                  |
| **Part**                 | Message / Artifact 内最小内容单元：TextPart、FilePart、DataPart     | 文本、文件引用、结构化数据                |
| **Artifact**             | agent 产出的结果（文档、代码、结构化数据、报告）                    | 交付记录、spec、报告、代码变更集          |
| **Task Status Update**   | 任务进度状态事件                                                    | 进度、阻塞、等待输入通知                  |
| **Task Artifact Update** | 工件产出 / 更新事件                                                 | 新工件落库通知                            |
| **contextId**            | 同一主题下多个任务的分组标识                                        | 同一批次 / 同一变更的任务归组             |

### 4.2 任务生命周期状态

对齐 A2A v1.0 状态枚举，分活跃、中断、终态三类：

| 状态             | 类型 | 含义                                           |
| ---------------- | ---- | ---------------------------------------------- |
| `SUBMITTED`      | 活跃 | 任务已提交并被确认                             |
| `WORKING`        | 活跃 | agent 正在处理                                 |
| `INPUT_REQUIRED` | 中断 | 需要人或另一组件补充输入才能继续               |
| `AUTH_REQUIRED`  | 中断 | 需要认证 / 授权                                |
| `COMPLETED`      | 终态 | 成功完成                                       |
| `FAILED`         | 终态 | 因错误结束，附原因                             |
| `CANCELED`       | 终态 | 完成前被取消，释放资源                         |
| `REJECTED`       | 终态 | agent 判定不执行该任务（创建时或之后），附理由 |

**任务不可变原则**：任务进入终态后不能重启；细化、返修、跟进必须在同一 `contextId` 下发起新任务，使每个任务保持清晰、不可变的工作单元。

### 4.3 有效迁移约束

- 活跃态之间：`SUBMITTED → WORKING`；
- 活跃 → 中断：`WORKING → INPUT_REQUIRED` / `AUTH_REQUIRED`；中断解除后回到 `WORKING`；
- 任意活跃 / 中断态 → 终态；
- **终态不可逆**：不允许从 `COMPLETED` 回到 `WORKING`；
- 无法解析请求或遇未预期错误 → `FAILED` 并附说明；
- fire-and-forget 场景可取消孤儿任务（`CANCELED`）以释放资源。

### 4.4 任务契约 schema（任务单标准字段）

| 字段组     | 字段                                                   | 说明                           |
| ---------- | ------------------------------------------------------ | ------------------------------ |
| 标识       | taskId、contextId、type、title、createdAt、baselineRef | 唯一标识、归组、类型、版本锚点 |
| 目标       | objective、successCriteria、outOfScope                 | 做什么、验收标准、明确排除     |
| 上下文     | references、priorTasks、constraints                    | 引用工件、前置任务、硬约束     |
| 切片       | scope（文件 / 模块 / 实体 / 接口清单）、exclusions     | 纳入范围与排除项               |
| 能力要求   | requiredSkills、requiredTools、agentRole               | 路由到正确 agent 所需能力      |
| 交付物     | artifacts 清单、artifactSchema、deliveryPath           | 产出类型、结构、落点           |
| 质量门禁   | gates（命令 / 检查 / 阈值）、evidenceFormat            | 必须执行的检查与证据格式       |
| 风险与策略 | policyRefs、escalationTriggers                         | 引用的策略规则、升级条件       |
| 元数据     | priority、dependsOn、deadline、retention               | 调度依赖与保留策略             |

### 4.5 回执 / 工件契约 schema

| 字段组 | 字段                                                                    | 说明               |
| ------ | ----------------------------------------------------------------------- | ------------------ |
| 落地   | changedFiles（added / modified / deleted）、artifactRefs                | 实际改动与工件引用 |
| 证据   | gateResults（命令、exit、error / warning、用例数 / 文件数）、reproNotes | 可复现的闸门证据   |
| 范围   | scopeCheck、parallelArtifactsExcluded、noOutscopeRefactor               | 隔离核对结果       |
| 契约   | contractChecks、contractRef、fieldAlignment                             | 口径与类型对齐结果 |
| 遗留   | backlogItems、openQuestions、manualReviewList                           | 既有债与待人工复核 |
| 偏差   | deviationTable（任务单写法 / 代码现实 / 处理 / 理由）                   | 与任务单的出入说明 |
| 状态   | finalStatus、reviewVerdict、verdictRationale                            | 终态与验收结论     |

## 5. 任务编排与依赖

### 5.1 任务 DAG

- Planner 将目标拆解为任务 DAG：节点为任务，边为依赖；
- 任务状态同时受自身生命周期与上游依赖约束；上游 `COMPLETED` 才解锁下游；
- 无依赖任务可并行；并行按域 / 文件切片隔离，避免同文件冲突。

### 5.2 调度与并发

- **任务队列**：就绪任务排队；Scheduler 按优先级、依赖、能力匹配分配；
- **Claim 锁**：任务被领用时写入锁记录（领取者、时间、租约）；租约超时自动释放，避免崩溃后悬挂；
- **并发隔离**：并行任务的文件切片不重叠；交付前做变更集冲突检查；
- **背压**：并发度受工具层与执行环境容量约束；超限任务排队而非抢占。

### 5.3 嵌套委派

- 子团队 leader 对上层屏蔽内部结构；
- 子团队内部可再派生子代理；跨层通信经 leader 汇总；
- 嵌套层级与 taskId 路径保留在 provenance 中，保证审计可追到根任务。

## 6. 上下文与记忆工程

### 6.1 上下文边界

- 每个子代理获得独立、最小化的上下文：任务契约 + 必要引用 + 分配到的工具集；
- 内部推理、草稿、中间过程不跨代理传播；对外只给契约字段与工件引用；
- 代理不假设其他代理记得历史对话；跨任务信息一律从 Memory Store / Artifact Store 读取。

### 6.2 记忆分层

| 记忆层   | 生命周期 | 内容                         | 存储                         |
| -------- | -------- | ---------------------------- | ---------------------------- |
| 工作记忆 | 任务内   | 当前任务的中间状态、临时结论 | 任务上下文 / State Store     |
| 共享记忆 | 跨任务   | 已确立的口径、约定、模块事实 | Memory Store（受控写入）     |
| 长期记忆 | 跨阶段   | 案例库、历史决策、经验教训   | Memory Store / 案例库        |
| 工件记忆 | 持久     | 交付物、报告、代码、规格     | Artifact Store（不可变版本） |

### 6.3 上下文压缩与传递

- 长任务做阶段性摘要与状态落盘，避免上下文膨胀导致漂移；
- 大产出直接写工件存储，对话内只传引用与关键结论；
- 记忆写入有审批或规则约束，防止错误结论被固化为共享事实。

### 6.4 上下文恢复

- 代理崩溃或会话重置后，依 taskId 从 State Store 读状态、从 Artifact / Memory Store 读事实重建上下文；
- 恢复不依赖任何对话历史；任务可在新代理实例上继续。

## 7. 工具与资源层（MCP）

### 7.1 标准原语

| 原语      | 用途                                                           |
| --------- | -------------------------------------------------------------- |
| Tools     | 可执行操作（仓库读写、运行测试、版本控制、检索、调用外部系统） |
| Resources | 可读数据与对象（文件、规格、知识库条目、配置）                 |
| Prompts   | 标准化提示模板与工作流入口                                     |

### 7.2 工具边界与权限

- 每个工具声明输入 schema、输出 schema、所需权限与副作用类型（只读 / 受限写 / 敏感操作）；
- 工具服务端收口权限校验与审计；agent 不直接持有底层连接句柄或内部配置；
- 不暴露通用仓储代理、底层查询选项或原始操作符给业务层；端口只收现有调用面；
- 敏感工具（提交、发布、外部系统写入）需对应审批节点与策略校验。

### 7.3 工具治理

- 工具注册与版本管理；能力变更走版本协商；
- 每次工具调用记录调用者、任务 ID、输入摘要、结果状态；
- 工具故障归入可靠性平面（超时、重试、降级），不在代理侧静默吞掉。

## 8. 工件与版本治理

### 8.1 工件模型

- 工件含：内容、contractRef（契约 urn）、provenance、版本号、依赖工件引用；
- 工件类型与结构由任务契约定义；结构化工件优先 DataPart，二进制 / 文档走 FilePart。

### 8.2 Provenance（来源追溯）

每个工件记录：产出 agent、任务 ID、contextId、基线版本（如 commit ref）、时间戳、输入工件、工具调用链摘要；保证结论可回溯到源头。

### 8.3 版本与不可变

- 已发布工件不可原地修改；修订产生新版本；
- 版本间差异可 diff；历史版本保留只读；
- 代码类工件经版本控制系统分组提交，提交与任务 ID 关联。

### 8.4 归档

- 终态任务的工件按阶段 / 批次归档；
- 回复原文、中间产物、正式交付物分类存放；归档不删除历史链接；
- 保留策略按工件类型定义（工作草稿短保留，交付记录与案例长期保留）。

## 9. 验收与评估平面

### 9.1 双层质量机制

| 层         | 机制                                               | 执行者                    |
| ---------- | -------------------------------------------------- | ------------------------- |
| 任务级验收 | 单任务交付核对（落地 / 证据 / 范围 / 契约 / 遗留） | Reviewer 角色             |
| 系统级评估 | 回归集、golden trace、质量门禁、指标趋势           | Eval 组件 + Observability |

### 9.2 任务级五类核对

1. **落地**：预期工件逐条存在且非空；变更清单与契约比对；构建产物 / 临时文件未混入；
2. **证据**：闸门命令、退出码、数字齐全且可复现；关键路径抽跑；失败项定性（确定性缺陷 / 偶发 flake）；
3. **范围隔离**：改动落在授权切片；策略边界未碰；并行产物未混入；无相邻重构；
4. **契约口径**：schema 与字段对齐；真相源唯一；消费端不复算口径；版本号随数据下发；
5. **遗留登记**：既有债入 backlog；未决项与人工复核清单完整；索引与归档完成。

### 9.3 验收结论分级

- **通过（COMPLETED）**：五项全清；
- **有条件通过**：主体合格，遗留显式登记且不阻塞，结论列清遗留与复核要求；
- **打回（REJECTED / 新任务返修）**：落地缺口、证据不实、越界改动或契约未对齐；写明原因与待补动作；终态任务不重启，返修新开任务。

### 9.4 系统级评估

- **回归集**：固定样例与黄金样本，每次批量变更后跑准确率 / 覆盖率回归；
- **Golden Trace**：标准任务的完整执行轨迹作为对照，新执行与之比对；
- **质量门禁**：单测覆盖率、类型检查、lint、边界断言、契约检查作为发布闸门；
- **持续度量**：任务通过率、返修率、平均耗时、工具失败率、成本、上下文长度趋势；
- **评估与线上监控分离**：离线回归集保证基线，线上 trace 监控异常漂移。

### 9.5 验收独立性

- Reviewer 与 Executor 为不同角色；初期由同一控制面兼任时，验收必须基于工件证据与抽跑复现，不接受执行侧自述通过；
- 验收阶段发现的新问题另开任务，不在当前任务顺手修复。

## 10. 可靠性设计

| 机制       | 设计                                                           |
| ---------- | -------------------------------------------------------------- |
| 幂等       | 任务 ID + 工件版本保证重复执行不产生重复副作用；写操作带幂等键 |
| 重试与退避 | 可恢复错误指数退避重试，限次；不可恢复错误直接 `FAILED`        |
| 超时       | 任务级与工具级超时；超时任务标记中断 / 失败并释放资源          |
| 断路器     | 某工具或下游连续失败达阈值后熔断，避免级联故障                 |
| 死信队列   | 反复失败的任务进入死信队列，附完整错误上下文，转人工处理       |
| 崩溃恢复   | 状态与工件外置；新实例从 State Store + Artifact Store 重建续跑 |
| 并发锁     | claim 租约 + 文件切片隔离；冲突检测在交付前执行                |
| 任务不可变 | 终态不重启；返修新开任务，避免状态混杂                         |
| 版本锚点   | 任务记录基线版本；验收核对未基于过期基线                       |

## 11. 安全与策略平面

### 11.1 权限模型

- 角色 → 工具 → 资源三级授权；最小权限默认；未声明能力拒绝；
- 工具副作用分级（只读 / 受限写 / 敏感操作）；敏感操作走审批；
- Secrets 由独立安全存储管理，不进入任务文本、日志或工件。

### 11.2 策略即代码

- 红线、边界规则、口径约束表达为机读策略（规则集 / 校验器 / 边界断言），在工具层与验收平面自动执行；
- 策略变更经审批留痕；任务可引用策略版本；
- 策略校验与人工判断分层：机器可判的边界自动拦，语义争议转人。

### 11.3 注入与数据防护

- 外部输入（代码、文档、检索内容）视为不可信；工具调用与指令解析隔离；
- 隐私分层：敏感对话原文不进工件、日志与记忆；只输出码、计数与机制描述；
- 工件与日志做敏感信息脱敏；访问范围按角色控制。

### 11.4 审计日志

- 关联 ID 贯穿任务、消息、工具调用、工件、提交；
- 审计日志追加写、防篡改；支持按任务 / agent / 时间检索与回放；
- 协议本身不提供防篡改审计时（见 §15 注），由本平面的工件与日志兜底。

## 12. 人机协同（HITL）

### 12.1 两种模式

- **Human-in-the-loop（环内）**：关键节点暂停等待人确认后继续（如敏感动作、策略例外、发布）；
- **Human-on-the-loop（环上）**：系统自动运行，人监控并在异常 / 升级时介入。

目标态：常规任务环上自动跑；策略例外、敏感动作、分歧仲裁走环内审批节点。

### 12.2 审批节点与升级触发

| 触发条件                  | 动作                                      |
| ------------------------- | ----------------------------------------- |
| 任务触及红线 / 策略边界   | 暂停执行，转人裁决                        |
| 同一任务失败 / 打回达限次 | 升级人工，附失败证据与可选路径            |
| 契约冲突且无先例可依      | 暂停，编排层取证后回写契约，必要时人拍板  |
| 需要外部输入 / 认证       | `INPUT_REQUIRED` / `AUTH_REQUIRED` 中断态 |
| 发布 / 对外系统写入       | 审批节点                                  |

### 12.3 人工边界

人负责：目标与方向、策略例外批准、技术路线选型、跨任务架构变更、验收分歧仲裁、最终发布。人不负责：单任务实现、逐条数字核对、模板化归档。

### 12.4 升级消息标准

升级请求携带：任务 ID、上下文、当前状态、已尝试路径、失败证据、可选方案、建议决策点；使决策者无需翻会话即可判断。

## 14. 协议与框架选型

### 14.1 协议层

| 层           | 标准                  | 定位                                 | 采用建议                                                |
| ------------ | --------------------- | ------------------------------------ | ------------------------------------------------------- |
| 工具接入     | **MCP**               | agent → 工具 / 资源 / 提示           | 目标态标准；工具能力以 MCP 原语暴露                     |
| 代理协作     | **A2A**               | agent 发现、任务委托、状态与工件回传 | 目标态标准；Agent Card + Task + Message + Artifact 模型 |
| 工作流持久化 | durable workflow 模式 | 状态机持久化、重试、回放             | 编排层实现选择，可由框架或自研状态机承担                |

> ACP 已并入 A2A；新系统面向 A2A，不引入 ACP 并行栈。

### 14.2 编排框架选型维度（不绑定具体厂商）

| 维度       | 考察点                                                |
| ---------- | ----------------------------------------------------- |
| 状态管理   | 是否支持 checkpoint、任务状态持久化、崩溃恢复         |
| 模式支持   | supervisor / team / pipeline / 并行子代理是否原生支持 |
| 协议兼容   | MCP 接入便利度；A2A 任务模型映射能力                  |
| 可观测     | trace、事件流、与外部监控的对接                       |
| 扩展与隔离 | 子代理上下文隔离、工具权限边界、嵌套委派              |
| 生态与锁定 | SDK 绑定程度；状态与工件是否可导出为开放格式          |
| 运行形态   | 本地进程 / 服务化部署；是否适配现有执行环境           |

候选参考：LangGraph（图状态机）、CrewAI（角色任务团队）、AutoGen（对话与群聊）、OpenAI Agents SDK（handoff / routine）；亦可自研轻量状态机 + 开放存储。选型以 §14.2 维度打分，优先状态与工件可导出、协议开放者。

### 14.3 存储选型维度

- **Task State Store**：任务状态机读写；要求事务、并发锁、租约、可查询；实现可为 DB 或文件索引，接口抽象隔离；
- **Artifact Store**：大版本工件、provenance、检索；与版本控制系统互补；
- **Memory Store**：受控读写的共享 / 长期记忆；带来源与审批；
- 存储格式采用开放标准（结构化 JSON / Markdown / 文件），避免锁定私有格式。

### 15.2 协议已知局限（需由本架构兜底）

公开研究指出，现有互通协议在原生语义上缺少：成员准入与移除、结构化辩论（challenge / response）、表决、异议表达、到人权限的升级触发条件、防篡改审计日志与回放。A2A 的 Traceability 扩展只提供关联 ID 做分布式追踪，不等于防篡改证据链。
**对策**：治理、表决 / 异议、升级与审计由本架构 §11 安全策略平面、§12 人机协同、§8 工件 provenance 兜底；不假设协议层原生提供这些能力。
