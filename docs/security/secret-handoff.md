# 跨机密钥交接规程（secret-handoff）

适用范围：同一个仓库、多台开发/编排机器（当前为 `DESKTOP-6U804B0` 与 `DESKTOP-E3EVQ9P`）之间传递**运行时密钥**（模型 API Key、第三方凭据、数据库口令）。

本文件只规定**传递方式与验收口径**，不记录任何密钥值。

## 1. 原则（四条，违反即事故）

1. **密钥永不入库**：`.env` 由 `.gitignore` 忽略；任何提交里出现 `KEY=真实值` 都按泄漏处理（见 §7）。
2. **密钥不进日志与状态面**：编排事件、回执、快照、错误栈、截图都不允许带值。体检工具只输出键名与长度（`pnpm env:doctor` 已按此实现）。
3. **密钥不进聊天记录 / 任务单 / 交付记录**：文档里只用键名占位，如 `LLM_DOUBAO_API_KEY=<由接收方在本机填入>`。
4. **一把钥匙一条交接记录**：每次跨机传递都要有回执（§5），否则视为未交接。

## 2. 当前密钥清单（按用途分组）

| 分组              | 键名                               | 承载能力                      | 备注                                       |
| ----------------- | ---------------------------------- | ----------------------------- | ------------------------------------------ |
| 渲染兜底 provider | `LLM_DOUBAO_API_KEY`               | 豆包（火山方舟）第二 provider | 与 `ENGINE_RENDER_FALLBACK_PROVIDERS` 配套 |
| 渲染路由开关      | `ENGINE_RENDER_FALLBACK_PROVIDERS` | 启用哪些兜底 provider         | 非密钥，但决定 key 是否被消费              |
| 语音链路          | `MINIMAX_*`                        | ASR / TTS                     | 共享值，改动须同步两台                     |
| 邮件 / 短信       | `SMTP_*`、`SMS_*`                  | 通知                          | 测试环境可用占位                           |
| 数据库            | `DB_*`                             | MySQL                         | 指向开发库，不入生产                       |

清单以 `.env.example` 的生效行为准（它是部署契约，由 `test/config/wp25-env-example-coverage.spec.ts` 双向守卫）。本表只维护“跨机必须一致”的那些键。

## 3. 三种交接方式与取舍

| 方式                     | 做法                                                                                      | 优点                                 | 代价                                          | 判断                 |
| ------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------ | --------------------------------------------- | -------------------- |
| A. 凭据管理器            | 两台机器登录同一密码库（1Password / Bitwarden），各自取用                                 | 无明文经过聊天与终端；可审计取用记录 | 需要账号与客户端；国产环境可用性不稳          | 有条件时优先         |
| B. 一次性人工粘贴 + 回执 | 发起方把值粘到接收方本机 `.env`（面对面、远程桌面或受控剪贴板），随后双方各留一条交接回执 | 零基础设施；当场可验证               | 值在传输通道上存在一次；依赖人工纪律          | **当前默认**（§4）   |
| C. SOPS + age            | 加密后的密文入库，机器各自持有私钥解密                                                    | 密文可入库、可版本化                 | 引入工具链与私钥管理；两台 Windows 需额外装配 | 团队规模扩大后再评估 |

**选定**：现阶段用 B，并在 B 之上加两道机器校验（`env:doctor --keys` 与一次真实调用探测），把“人工纪律”变成“可验证事实”。条件具备时升级到 A。

## 4. 交接流程（六步，缺一不可）

1. **发起方**在任务单/消息里只写键名与用途，不写值：`LLM_DOUBAO_API_KEY`（豆包方舟 v3）。
2. **发起方**确认本机已可用：`pnpm env:doctor --keys LLM_DOUBAO_API_KEY,ENGINE_RENDER_FALLBACK_PROVIDERS` 通过，且一次真实调用返回 200（见 §6）。
3. **传递**：通过受控通道把值交给接收方，接收方在本机 `.env` 填入（追加，不覆盖其它键）。
4. **接收方**自检：同一条 `pnpm env:doctor --keys ...` 必须 PASS；`git status` 中不得出现 `.env`。
5. **回执**：接收方写一条交接回执（§5），发起方确认后各自留存。
6. **对账**：双方回执里的键名集合必须一致；不一致按“未交接”处理。

## 5. 交接回执模板

存放位置：`docs/team/agent-orchestration/transport/handovers/secret-<日期>-<键名>.md`（transport 为运行态收件箱，不入库正文）。

```markdown
# 密钥交接回执 · <键名>

- 键名：LLM_DOUBAO_API_KEY
- 用途：豆包（火山方舟）渲染兜底 provider
- 值指纹：sha256 前 8 位（只记指纹，不记值）
- 发起方：DESKTOP-6U804B0 / <角色>
- 接收方：DESKTOP-E3EVQ9P / <角色>
- 交接时间：2026-11-21T01:40:00+08:00
- 校验命令：pnpm env:doctor --keys LLM_DOUBAO_API_KEY,ENGINE_RENDER_FALLBACK_PROVIDERS
- 校验结果：PASS（键存在、值非空、.env 未被跟踪）
- 连通探测：<命令> → HTTP 200 / 模型返回正常
- 备注：<轮换计划 / 到期时间>
```

指纹算法：`printf %s "$VALUE" | sha256sum | cut -c1-8`（或 PowerShell `-join` 等价实现）。指纹用于“两台机器配的是不是同一把”，不泄露值。

## 6. 校验命令（两台机器都要能跑）

```powershell
# 键存在 + 值非空 + .env 未被跟踪（交接验收口径）
pnpm env:doctor --keys LLM_DOUBAO_API_KEY,ENGINE_RENDER_FALLBACK_PROVIDERS

# 全量体检（缺键、空值、疑似泄漏、跟踪状态）
pnpm env:doctor

# 机器可读，用于回执留档
pnpm env:doctor --keys LLM_DOUBAO_API_KEY --json
```

判定：`--keys` 指定的键缺失或为空一律 `error` 并 exit 1（不受 `--strict` 影响）；全量模式下缺键只是 warning。

## 7. 轮换与违规处置

**常规轮换**（建议每 90 天或人员变动时）：

1. 在控制台新建 key，旧 key 保持可用直到两台机器都切换完成；
2. 两台机器各自更新 `.env` 并跑 §6 校验；
3. 两台都 PASS 后吊销旧 key；
4. 更新两条交接回执的指纹与时间。

**发现泄漏**（密钥出现在提交、日志、截图或聊天记录）：

1. 立即在控制台**吊销**该 key（轮换优先于排查）；
2. 检查 `git log -S '<值片段>' --all` 是否入过库；入过库则按事故处理（改写历史 + 通知协作者）；
3. 新 key 走 §4 流程重新交接；
4. 在 `docs/security/` 追加一条事故记录（时间、暴露面、处置、复发预防）。

## 8. 已知边界

- 本规程不覆盖生产环境密钥（生产走部署平台注入，见 `docs/runbooks/docker-deploy.md`）。
- 方式 B 的传输通道安全依赖操作者判断（受控剪贴板 / 远程桌面 / 当面），没有密码学保证。
- `env:doctor` 只验证“键在、值非空、未跟踪”，不验证“值是否有效”——有效性靠一次真实调用探测（§6）。
- 交接回执放在 transport 收件箱，不随仓库分发；跨机可见性依赖各自先 fetch 到同一份文档（规程本身入库，回执不入库）。
