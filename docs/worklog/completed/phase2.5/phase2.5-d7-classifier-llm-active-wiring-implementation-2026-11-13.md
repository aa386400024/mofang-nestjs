### (d) 有无被误判为「装配层小改」、实际需碰 core 的隐式耦合？

**结论：不需碰 core；但「纯装配层改动」这个判断本身是错的 —— 还必须改一行 adapter 业务分支。不改就是接线即埋雷。**

**① core 侧零耦合（逐段核查，不是靠猜）：**

- `in-memory-engine-session.ts:419-426` 已有 `classifyAsync ? await : classify` 的**互斥**分支，D-1 已把异步口开好 —— 内核不需要任何改动。
- `DELTA_TABLE` 两类新 kind 种子仍是 `ZERO`（`state-transition.ts:358-359`，D-2 已落）→ 模型判 `holding_present` / `cold_absent` 那轮 delta **逐字为零**，不触发任何数值路径变化。
- core 内**唯一**按事件 kind 分支的地方是 `personality-modulator.ts:313`（`agreeableness` 的 trust 调节门槛：本轮**有 empathy 事件**才调节）。生效轨下该门槛跟着**模型判定**走（模型判 `holding_present` 而规则轨判 `empathy` → 本轮不做该调节）。这是「模型事件替换规则轨事件」的**必然推论**，语义正确，**登记为观测点不改代码**（见 §8 L-2）。
- D-2 遗留 L-8 提到的 `hasNonNeutralEvent`，实测**不在 core**，在**评测层** `src/auto-practice/metrics/batch-metrics.compute.ts:208`（零变化场次细分：事件层非 neutral = 合理封闭豁免 / 纯 neutral 空转 = 计入失效）。生效轨下两类新 kind 会被判为非 neutral → 该场从「空转」改判「合理封闭」。**属评测口径，留标定批次反向取证**，本单不改（也不需要改 core）。

**② 真正的隐式耦合：低置信泄漏（本单修掉的那处）。**

开工单 §4.2 写「既有实现，本单复核不改逻辑」，但复核**发现该逻辑在接线后不成立**：

```ts
// 接线前 (D-1 留下)
if (mode === 'llm_active' && outcome.labels) {
  return outcome.labels.coreKinds.map((kind) => ({ kind, matchedTerms: [], strength: 1 }));
}
```

- `runModelTrack` 的**低置信**路径返回 `{ labels: <非 null>, fallbackReason: 'low_confidence' }` —— 标签**带着**回来（模型标签仍要进观测），但这一轮**判定不可用**、**已回落**。
- 原分支只看 `outcome.labels`，**不判 `fallbackReason`** → 低置信轮会把模型事件**当生效结果**送进 core events。
- **为什么 shadow 模式下看不见**：shadow 分支永远返回 `ruleEvents`，压根不走这条路径。**接线 = 把这条分支暴露到生产路径**。
- **违反的硬约束**：任务单硬约束 4「回落路径（… / 低置信 / …）一律返回规则轨等价事件」。不修就是**违反红线**。
- **修法**：条件加一个 `outcome.fallbackReason === null`（**一行**），不动熔断 / 低置信 / 超时任何参数，不动回落代码（回落代码仍只有 `this.rule.classify` 一处）。

```ts
// 接线后 (D-7)
if (mode === 'llm_active' && outcome.labels && outcome.fallbackReason === null) {
  ... // 只有「模型轨真的成功」才替换规则轨结果
}
```

**③ 其它候选耦合的排除结论**：审计落库结构（消费内核出参，不产事件）、指标字典（纯数值指标，无事件种类依赖）、审议门（两套开关隔离，见 T2）、规则轨词表（未动）、DB migration（未动）—— 全部排除。
