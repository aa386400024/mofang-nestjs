## 一、背景

### 1.1 现在是什么状态

R9 灰度切换开关做完了，审议已经可以配置生效（shadow / rule_only / llm_active 三模式）。

但现在的审议 prompt 传的是什么？——**完整对话原文**：
- 咨询师说的话（`counselorText: input.userText`）
- AI 来访者说的话（`visitorText`）

这两段原文原样拼进 prompt，发给第三方大模型（Minimax）。

### 1.2 问题是什么

**两个问题一起炸：**

**问题 1：合规问题（R6）**
- 咱们是心理类 App，对话内容属于敏感数据类别
- 即使是训练场景（咨询师跟 AI 来访者对练），对话原文传给出境第三方模型，也涉及数据出境合规
- 蓝图 §3.1 边界 3 明确要求：「审议 prompt 不传完整用户原文，只传结构化事件分类」

**问题 2：成本问题（R8）**
- 每轮审议都传完整对话原文，prompt 很长
- 30 轮下来 prompt 破 10k token，成本和延迟都扛不住
- 蓝图 §3.2 边界 7 明确要求：「审议输入不是全量传，是相关维度传」

### 1.3 为什么这个是最优解

咱们的场景是「咨询师跟 AI 来访者做训练」，审议的本质是什么？——**评估这一轮对话后，BDI 状态变化合不合理**。

那审议需要传完整对话原文吗？不需要。只需要传：
- 结构化事件分类（比如"咨询师表达了共情"）
- 状态变化前后的对比（trust 0.5 → 0.58）
- 角色设定简述（依恋风格、人格基线）
- 风险等级（低/中/高）

**为什么这是最优解：**
1. **合规问题从根上解决** —— 不传原文 = 心理数据不出境
2. **成本问题顺便解决** —— 上下文短了，token 成本直接降一半
3. **审议质量不会降太多** —— 审议的核心是"这个 delta 合不合理"，不是"这句话说得对不对"

## 二、目标

### 2.1 本单要做什么

**把审议输入从"完整对话原文"改成"结构化数据 + 状态对比"，合规 + 成本双解决。**

具体来说：
1. **定义结构化输入 schema** —— 审议 prompt 的输入格式重新设计，不传原文
2. **事件分类器** —— 从咨询师发言和 AI 来访者发言中，提取结构化事件分类（比如 empathy_partial / confrontation_soft / ...）
3. **状态对比数据** —— 当前状态快照 + 上一轮状态快照，让 LLM 看到变化幅度
4. **角色简述** —— 角色 ID + 依恋类型 + 核心信念摘要 + 阻抗基线 + 大五人格简述
5. **高风险分流** —— 风险等级高的轮次，永远不跑 LLM 审议，直接走规则
6. **prompt 模板重写** —— 基于新的结构化输入，重写系统 prompt 和用户 prompt

### 2.2 本单不做什么（边界）

| 不做的 | 为什么 | 什么时候做 |
|---|---|---|
| 触发式闸门（什么时候跑审议） | 另一个 WP（WP-C） | WP-C |
| 版本锁定（模型/prompt 版本号） | 另一个 WP（WP-B） | WP-B |
| 考核场景纯规则路由 | 另一个 WP（WP-B） | WP-B |
| 脱敏后传原文 | 不需要——咱们直接不传原文，更彻底 | —— |
| 事件分类器用 LLM 做 | 先用规则做（基于现有事件词典），后面再优化 | 后续按需 |
| engine-core 改代码 | 审议输入在适配层，内核不动 | —— |

## 三、方案设计

### 3.1 核心思路：结构化输入，不传原文

**现在的审议输入：**
```
系统 prompt：角色设定 + 临床约束 + 输出格式要求
用户 prompt：
  【本轮咨询师发言】"我能感受到你现在很焦虑，能跟我多说一点吗？"
  【本轮来访者反应】"嗯...我最近确实睡不好，总是担心工作的事。"
  当前状态快照：{ trust: 0.5, resistance: 0.3, ... }
```

**改成：**
```
系统 prompt：角色设定 + 临床约束 + 输出格式要求 + operatorTags 枚举表
用户 prompt：
  【本轮事件分类】empathy_partial, open_question
  【状态变化对比】
    trust: 0.500 → 0.520 (+0.020)
    resistance: 0.300 → 0.285 (-0.015)
    emotionValence: -0.100 → -0.080 (+0.020)
  【角色基线】
    依恋类型：回避型
    阻抗基线：0.35
    大五人格：低宜人性 + 高神经质
  【风险等级】低
```

**关键变化：**
- ❌ 不传咨询师说的具体内容
- ❌ 不传来访者说的具体内容
- ✅ 传事件分类（从发言中提取的结构化标签）
- ✅ 传状态变化对比（前后值 + delta）
- ✅ 传角色基线（LLM 需要知道基线才能判断变化幅度合不合理）

### 3.2 事件分类器：先用规则做

现在引擎里已经有 `event-lexicon.ts`（事件词典）和 `rule-based-classifier.ts`（规则分类器）。

**做法：**
- 复用现有的事件分类机制，从咨询师发言和来访者发言中提取事件标签
- 提取出来的事件标签，作为审议输入的一部分
- 不用 LLM 做分类——先用规则，后面再优化

**为什么先用规则：**
- 咱们已经有事件词典了，直接复用
- 规则分类器是确定性的，可复现
- 后面如果发现规则分类不准，再换成 LLM 做

### 3.3 高风险分流：永远不跑 LLM 审议

**红线：**
- 风险等级高（自杀倾向 / 自伤风险 / 危机等级）的轮次，永远不跑 LLM 审议
- 直接走规则算子，状态变化完全由规则决定
- 这是合规底线，没有商量余地

**做法：**
- 审议钩子入口处先检查风险等级
- 高风险 → 直接返回规则 delta，不跑 LLM
- 低风险 → 正常跑 LLM 审议

### 3.4 prompt 模板重写

基于新的结构化输入，重写 prompt：

**系统 prompt：**
- 角色设定摘要（依恋类型 / 核心信念 / 阻抗基线 / 大五人格简述）
- 临床约束（不能给建议 / 不能做诊断 / 只做状态变化评估）
- 输出格式要求（JSON schema）
- operatorTags 枚举表（告诉 LLM 有哪些标签可选）

**用户 prompt：**
- 本轮事件分类（empathy_partial, open_question, ...）
- 状态变化对比（前后值 + delta）
- 记忆召回 Top3 摘要（如果有的话）
- 风险等级

**为什么这样设计：**
- 系统 prompt 稳定（每轮都一样），只有角色设定部分变
- 用户 prompt 是结构化数据，不是自然语言，token 消耗少
- LLM 的任务很清晰："基于这些结构化数据，判断这个状态变化合不合理，要不要调整 delta"

## 六、边界（红线）

### 6.1 engine-core 纯层红线

- ❌ 不改 `src/engine-core/` 下任何文件
- ✅ 所有改动都在 `src/engine-adapters/deliberation/` 下
- ✅ 审议输入的组装在适配层做，内核不知道输入是什么

### 6.2 零回归红线

- ❌ 不改现有审议的输出格式（deltas + reason + operatorTags + intentionShift）
- ❌ 不改现有审议钩子的调用方式
- ✅ 只是改"传给 LLM 的输入是什么"，不改"LLM 输出什么"

### 6.3 合规红线

- ❌ 高风险轮次永远不跑 LLM 审议，没有例外
- ❌ 审议 prompt 里永远不出现对话原文，没有例外
- ✅ 风险等级判断复用现有的 PsyGUARD 探测 + 本地规则引擎
